<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated JWT -> events RLS | A logged-in user (any org) querying `events` — untrusted; must only see events they participate in or own a capture of |
| authenticated JWT -> call_participants RLS | Existing boundary; the new columns must not widen the readable audience |
| foreign-org JWT -> events | A user in org B must read ZERO rows for an event whose only capture is owned by org A |
| service_role -> events/call_participants | Trusted; Phase 31+ matching engine writes via service-role edge functions only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-02-01 | Information Disclosure / Elevation of Privilege | new `events` table | mitigate | ENABLE + FORCE ROW LEVEL SECURITY on events, explicit participation/ownership SELECT policy, service-role-only writes — mirrored from the already-audited `call_participants` pattern (20260309120000). A table with RLS enabled but no policy is deny-by-default; FORCE prevents the table owner bypassing it. Proven by Plan 03's bespoke isolation test (positive + negative). HIGH severity — blocks merge if the policy is missing/permissive. |
| T-30-02-02 | Information Disclosure | events RLS predicate | mitigate | Use `auth.email()` / `auth.uid()` only — never a raw `auth.users` join (403 or email leak; this exact bug was fixed once in 20260309100000). `LOWER(auth.email())` matches lowercase-stored participant emails, avoiding a silent false-negative. HIGH severity. |
| T-30-02-03 | Elevation of Privilege | events RLS (copy-paste risk) | mitigate | Explicitly add NO org-admin bypass on events (recordings HAS one; events must NOT — EVT-04/ORG-04). A reviewer pattern-matching against recordings' RLS could add it by habit; the acceptance criteria assert its absence. HIGH severity. |
| T-30-02-04 | Elevation of Privilege | recordings/call_participants existing RLS | mitigate | This migration adds only new nullable columns — it adds NO new predicate to any existing recordings/call_participants policy, so no existing row's audience widens. Proven by Plan 03's byte-identical regression (which is also an RLS-non-regression check). |
