# Phase 6.1: MCP Subdomain Routing - Context

**Gathered:** 2026-06-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 6.1 delivers per-org (and optionally per-workspace) subdomain MCP URLs of the form `{orgslug}.callvaultai.com/mcp` and `{orgslug}-{wsslug}.callvaultai.com/mcp`, enabling multi-org operators to hold simultaneous MCP connections in Claude Desktop without origin collisions. It includes a new Cloudflare Worker for subdomain routing, slug schema + backfill migrations, OAuth consent page security hardening, and seven Critical/High security gates that must be verified before wildcard DNS is provisioned. Backward compatibility with `mcp.callvaultai.com` and `api.callvaultai.com/mcp` is preserved throughout via the existing api-proxy Worker.

</domain>

<decisions>
## Implementation Decisions

### Plan Structure
- **D-01:** One GSD PLAN.md per named feature from the execution plan (14 plans total). Each plan covers one atomic deliverable from the execution plan's feature list. Wave dependencies go in frontmatter `depends_on` fields, not in task grouping. The 14 features are: sec-worker-bypass, sec-jwt-fix, sec-dcr-phishing, sec-revocation-complete, sec-workspace-param, sec-worker-headers, sec-multiorg-grant, sec-tool-audit, sec-enumeration, sec-slug-tombstone, slug-schema, worker-routing, oauth-auth-screen, ui-url-builder. (Note: auth-slug-resolution, protocol-subdomain, oauth-metadata-scoped, and backward-compat from Wave 4 are sub-features of worker-routing and should be tasks within that plan, not separate plans.)

### Security Gate Sequencing
- **D-02:** All 7 Critical/High security gates (sec-worker-bypass, sec-jwt-fix, sec-dcr-phishing, sec-slug-tombstone, sec-revocation-complete, sec-workspace-param, sec-worker-headers) must be verified green before wildcard DNS is provisioned. This is a hard gate — wildcard DNS provisioning is a manual Cloudflare step that does NOT happen in any GSD plan; plans must flag it as a post-execution manual action.
- **D-03:** sec-enumeration (MEDIUM severity) does NOT block DNS provisioning. It runs after sec-worker-bypass but can complete in parallel with Wave 3 work.
- **D-04:** Wave 1 security fixes (all except sec-worker-bypass) are fully independent of each other and of slug/worker work. They can execute concurrently.
- **D-05:** Wave 1b (sec-worker-bypass) is also independent of Wave 1 fixes but is a prerequisite for sec-enumeration (Wave 2) and for the internal-secret header in the new subdomain Worker (Wave 4).

### Slug Schema and Backfill
- **D-06:** **Option A — auto-generate slugs for all existing orgs/workspaces.** On migration, slugs are derived from the org/workspace name: lowercase, strip all non-alphanumeric characters, truncate to 40 chars, append `-2` / `-3` etc. on collision. All existing orgs and workspaces receive a subdomain URL automatically on day 1 after migration. Rationale: Option B (leave NULL until admin sets slug) means zero existing users get the new feature on day 1, which defeats the purpose of the migration. Auto-generation from name is safe because tombstone tables prevent a future org from re-registering a slug that was ever used, and the `^[a-z0-9]+$` constraint ensures deterministic generation. Any org whose auto-generated slug collides gets a numeric suffix that remains stable.
- **D-07:** Slug format is locked by ISA constraint: `^[a-z0-9]+$` (alphanumeric only, NO hyphens). Maximum 40 characters. Combined subdomain format: `{orgslug}-{wsslug}.callvaultai.com` — the hyphen separator is unambiguous because neither slug can contain a hyphen.
- **D-08:** Tombstone tables (org_slug_tombstone, workspace_slug_tombstone) must exist BEFORE any slug is ever written. Migration order: tombstone tables → slug columns + backfill → Worker deployment.

### Worker Architecture
- **D-09:** New dedicated Cloudflare Worker at `cloudflare/mcp-subdomain-worker/worker.ts` — do NOT extend the existing `cloudflare/api-proxy/worker.ts`. The existing Worker handles api.callvaultai.com routing; the new Worker handles *.callvaultai.com/mcp subdomain routing. Both coexist via separate Cloudflare Worker routes.
- **D-10:** The new Worker injects `x-callvault-host` (the full subdomain hostname), `x-callvault-org-slug` (extracted from first segment), and `x-callvault-internal-secret` before forwarding to mcp-server. This is the slug-resolution handshake between Worker and Edge Function.
- **D-11:** Backward-compat (legacy mcp.callvaultai.com and api.callvaultai.com/mcp URLs) is handled by the EXISTING api-proxy worker — it adds a `Deprecation: true` header and continues proxying without breaking existing tokens.
- **D-12:** Worker development: use `wrangler dev` locally with `--env local` for pre-deploy testing. The wrangler OAuth login is already available on this machine (per STATE.md).

### Auth and Slug Resolution in Edge Functions
- **D-13:** auth.ts receives the subdomain slug via `x-callvault-org-slug` header injected by the Worker. It resolves slug → org_id via a DB lookup on `organizations.slug`. Workspace-scoped subdomains (orgslug-wsslug) also send `x-callvault-workspace-slug` injected by the Worker.
- **D-14:** On slug mismatch (token's org_id ≠ resolved org_id from subdomain), auth.ts returns 403 with JSON body `{"error": "token_org_mismatch"}`. Same pattern for workspace mismatch: 403 `{"error": "token_workspace_mismatch"}`.

### Consent Page Security UI
- **D-15:** Use existing component patterns throughout — no new custom components. First-time connection warning: Radix `Badge` component styled with `border-amber-400 text-amber-700 bg-amber-50` (amber/yellow, consistent with RiErrorWarningLine already imported). Client ID display: truncated to first 8 chars + `…` + last 4 chars rendered in a `<span className="font-mono text-xs">` inside the existing Card/CardContent layout. Redirect URI: show only the domain (scheme + host), not the full path, in normal body text. Advisory text ("Only approve if you initiated this connection") rendered in `className="text-muted-foreground text-sm"` below the redirect domain. RiShieldCheckLine (already imported) flanks the verified-domain display; RiErrorWarningLine (already imported) flanks the first-time badge.
- **D-16:** The consent page sec-dcr-phishing and oauth-auth-screen changes are BOTH to `src/pages/OAuthConsentPage.tsx`. They can be a single plan (sec-dcr-phishing handles the consent page security fields; oauth-auth-screen is the pre-scoped variant that uses the new subdomain URL as the `resource` — these are closely coupled and should be one plan).

### DNS Provisioning (Manual Step — Not in Any Plan)
- **D-17:** Wildcard DNS provisioning (`*.callvaultai.com` A/CNAME record pointing to Cloudflare Worker) is a MANUAL step performed in the Cloudflare dashboard AFTER all 7 Critical/High security gates are verified. No GSD plan automates this. The worker-routing plan should include a post-execution note listing the manual DNS steps.

<specifics>
## Specific Implementation Notes

- **First fix to ship:** `sec-jwt-fix` in `supabase/functions/mcp-server/auth.ts` — remove `readClientIdFromJwt()`, extract client_id exclusively from `authClient.auth.getUser(rawToken)` result
- **CALLVAULT_INTERNAL_SECRET:** 32-byte random hex; must be set in both Worker env vars AND Supabase secrets before sec-worker-bypass plan executes
- **Slug separator in combined subdomain:** single `-` between orgslug and wsslug (e.g., `acmecorp-sales.callvaultai.com`). Unambiguous because slugs are `^[a-z0-9]+$` (no hyphens in slugs themselves)
- **mcp.callvaultai.com stays fully functional throughout:** never touched by any plan except adding the `Deprecation: true` response header in the backward-compat task
- **Supabase network policy** for IP allowlist (ISC-4) is a Cloudflare IP range restriction — configured in Supabase dashboard, not in code

</specifics>
