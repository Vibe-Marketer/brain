Create migration `supabase/migrations/20260609000001_revocation_triggers.sql` that adds DB triggers covering BOTH `mcp_tokens` AND `mcp_oauth_client_grants` when workspace members or org members are removed.

<threat_model>
**ASVS Level:** L1

**Threats addressed by this plan:**
- [T-06.1-REV-01]: Elevation of Privilege — OAuth sessions survive workspace membership removal. After org/workspace member removal, mcp_oauth_client_grants.revoked_at remains NULL; OAuth-authenticated MCP calls continue to succeed. Mitigation: DB triggers cascade revocation to both mcp_tokens AND mcp_oauth_client_grants on membership DELETE (ISC-27–34).
- [T-06.1-REV-02]: Elevation of Privilege — Org member removal does not kill org-scoped tokens. Same pattern as above but at org scope. Mitigation: org_members DELETE trigger covers org-scoped records in both tables.
- [T-06.1-REV-03]: Elevation of Privilege — Supabase Auth JWT session survives membership removal. Even after DB revocation, a cached valid JWT continues to pass auth.getUser() until it expires. Mitigation: admin signOut(userId, 'global') invalidates all Supabase Auth refresh tokens for the removed user immediately (ISC-31).

**Residual risks:** JWT access tokens have a short expiry window (15 minutes by default in Supabase). Admin signOut invalidates refresh tokens immediately; existing access tokens will expire naturally within their TTL. For most cases, the DB trigger revocation (checked on every MCP call) catches this before the access token can be used successfully.

**Block condition:** Any HIGH severity threat not mitigated = executor must stop and surface to operator.
</threat_model>
