## Reusable Patterns

### Token Lookup

- Existing Obsidian code filters by `token_source = 'obsidian'` and `revoked_at IS NULL`.
- REST must improve this by distinguishing unknown token 401 from valid wrong-source token 403.
- Store `last_used_at` fire-and-forget after successful auth.

### Scope Resolution

- MCP `list_calls` uses workspace-scoped tokens directly and org-scoped tokens through `workspace_id` or org workspace lookup.
- Obsidian `resolveWorkspaceIds` validates `workspace_id` belongs to `org_id`.
- REST should centralize this as an API auth/scope helper for all handlers.

### Response Shape

- Existing `_shared/response.ts` uses `{ success, data }`, which does not match Phase 06.2's desired list envelope.
- REST should use local response helpers so MCP and other functions are not forced into the new contract.

### Settings UI

- Existing `ObsidianConnectorSection` already has token reveal, revoke confirmation, Pro gating, and ZIP export.
- Reuse the interaction patterns but rename and rewire around API tokens. Do not keep user-facing "Obsidian token" as the credential model.

## Risks

- `src/types/supabase.ts` currently does not show `token_source` in the `mcp_tokens` row excerpt, so migrations/types may be out of sync.
- Removing Obsidian-specific migration functions may require care if production already has them; prefer additive API-token migration plus code removal unless DB rollback/deletion is safe.
- Cloudflare worker route tests must prove `/v1/*` does not steal `/auth/v1/*` or MCP routes.
