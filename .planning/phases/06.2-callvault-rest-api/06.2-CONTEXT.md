# Phase 06.2: CallVault REST API - Context

**Gathered:** 2026-06-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 06.2 creates CallVault's canonical public REST API at `https://api.callvaultai.com/v1/*`. This API is for developers and future integrations, including Obsidian, and is separate from the MCP protocol surface.

The phase delivers API-token authentication, JSON REST endpoints for calls, contacts, workspaces, and speakers, Cloudflare proxy routing, and cleanup/migration away from the rushed unused Obsidian-specific API path where it conflicts with the canonical REST direction.

This phase is not an MCP tool expansion, not a Supabase raw `/rest/v1` exposure, not a public database-schema API, and not a broad write/admin API. It should not preserve Obsidian-specific backend/auth architecture for compatibility because the current Obsidian path has not been used by real users.

</domain>

<decisions>
## Implementation Decisions

### REST API Direction

- **D-01:** `api.callvaultai.com/v1/*` is the canonical machine API for CallVault integrations.
- **D-02:** Obsidian should use the canonical REST API over time instead of growing a separate `obsidian-sync` API contract.
- **D-03:** The existing Obsidian-specific implementation was done in haste and has no real user compatibility constraint. Planning and execution should remove, replace, or stop extending Obsidian-only backend pieces when they conflict with the REST API architecture.
- **D-04:** The REST API must be independent from MCP. It may reuse query/auth patterns, but it must not be implemented as MCP tools or return MCP response envelopes.
- **D-05:** Do not expose Supabase's generated PostgREST `/rest/v1` API as the public CallVault developer API. CallVault needs a deliberate product API with stable routes, stable JSON envelopes, scoped token auth, and schema-hiding boundaries.

### Public Route and Runtime

- **D-06:** Add `api.callvaultai.com/v1/*` routing through the existing Cloudflare API proxy.
- **D-07:** The preferred runtime is a dedicated Supabase Edge Function for the REST API, with internal routing for `/v1/calls`, `/v1/contacts`, `/v1/workspaces`, `/v1/speakers`, and any Obsidian-required call detail/transcript route that planning proves is necessary.
- **D-08:** Keep `api.callvaultai.com` as the public API host. Do not ask developers to use raw Supabase function URLs.
- **D-09:** The REST API should be versioned from day one under `/v1`.

### API Token Model

- **D-10:** REST API auth uses CallVault personal API tokens, not Supabase anon/service keys and not MCP OAuth/JWT protocol handling.
- **D-11:** Use the existing token storage foundation if practical: `mcp_tokens` already has `token_source` with allowed value `api`. The table name is unfortunate but centralizes ownership, org/workspace scope, revocation, and last-used tracking.
- **D-12:** API requests authenticate with `Authorization: Bearer <token>`.
- **D-13:** A valid non-revoked token whose `token_source` is exactly `api` can access the REST API according to its org/workspace scope.
- **D-14:** Missing, malformed, or unknown bearer tokens return HTTP 401 with a JSON error body.
- **D-15:** Tokens that exist but are for another source such as `mcp` or `obsidian` return HTTP 403 with a JSON error body.
- **D-16:** Planning should decide the cleanest token-generation path: either a `generate_api_token` RPC plus UI/service layer, or a generalized external-token generator that can replace the Obsidian-specific generator. The result must create `token_source = 'api'` tokens.
- **D-17:** Obsidian-labeled tokens should be API tokens with a label or integration hint, not a separate token universe, unless planning finds a concrete reason that separation is required.

### Endpoint Contract

- **D-18:** The required MVP endpoints are:
  - `GET /v1/calls`
  - `GET /v1/contacts`
  - `GET /v1/workspaces`
  - `GET /v1/speakers`
- **D-19:** Planning must evaluate whether Obsidian requires `GET /v1/calls/{id}` and/or `GET /v1/calls/{id}/transcript` in the first REST slice. If Obsidian cannot reasonably use the required MVP endpoints without a detail/transcript route, include the minimum route needed.
- **D-20:** All successful list responses use a stable JSON envelope such as `{ "data": [...], "pagination": { ... } }`.
- **D-21:** Error responses use a stable machine-readable JSON envelope, not blank text responses and not MCP JSON-RPC errors.
- **D-22:** Pagination should be consistent across list endpoints. Exact cursor-vs-offset mechanics are at planning discretion, but must be documented in the plan and covered by tests.
- **D-23:** REST response fields should be product-shaped and stable. Do not leak internal database shape just because Supabase can return it.

### Scope and Access

- **D-24:** Workspace/org access should honor the token's stored scope. Workspace-scoped tokens are limited to their workspace. Organization-scoped tokens can access workspaces in their organization and may accept an explicit `workspace_id` filter where appropriate.
- **D-25:** `/v1/workspaces` returns workspaces the authenticated API token is allowed to see.
- **D-26:** `/v1/calls`, `/v1/contacts`, and `/v1/speakers` must not cross organization/workspace boundaries. Existing `workspace_entries`, `contacts`, and `call_participants` access patterns should be reused or adapted rather than bypassed.

### Cleanup Direction

- **D-27:** Treat `supabase/functions/obsidian-sync` and `src/services/obsidian-tokens.service.ts` as migration/cleanup candidates. Do not build new canonical functionality around them unless planning proves a small piece should be reused.
- **D-28:** If removing Obsidian-specific code is low-risk, include it in Phase 06.2. If removal would expand the phase too far, disable/deprecate the path and capture deletion as a follow-up.
- **D-29:** Update active docs/UI copy so developers see the REST API as the integration path. Do not document the unused Obsidian-specific endpoint as the future path.

### the agent's Discretion

- Exact Edge Function file/module decomposition is at planning discretion, but should prefer a maintainable internal router and shared helpers over one long handler.
- Exact JSON field names are at planning discretion, as long as they are stable, documented in the plan, and avoid leaking accidental database internals.
- Exact API-token UI placement is at planning discretion, but it should be findable from settings/developer integration surfaces and should show generated tokens only once.
- Exact Obsidian export formatting route shape is at planning discretion if required, but formatting concerns should not force a separate auth/token/API architecture.

### Reviewed Todos

- `Resync updated Fathom call metadata` — reviewed but not folded. This belongs to connector/provider refresh behavior, not the REST API phase.
- `Research compliance certifications readiness` — reviewed but not folded. This is not needed to define or build the REST API.
- `Apply compliance posture fixes` — reviewed but not folded. Security hygiene is important, but this phase should focus on API auth, scoping, and route correctness rather than broad compliance posture cleanup.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `cloudflare/api-proxy/worker.ts`: already owns `api.callvaultai.com`, strips proxy headers, forwards host/path context, and routes to Supabase Edge Functions. It is the right place to add `/v1/*`.
- `supabase/functions/obsidian-sync/index.ts`: already demonstrates bearer lookup against `mcp_tokens` with a specific `token_source`, workspace resolution, paginated call listing, and transcript retrieval. It should inform the REST design but not remain the canonical Obsidian API.
- `supabase/migrations/20260608120000_obsidian_sync_token_label.sql`: already reserved `token_source = 'api'`, so Phase 06.2 can likely build API-token generation without a new table.
- `supabase/functions/mcp-server/tools/read/*.ts`: contain useful read access and shaping logic for calls, contacts, speakers, and workspace scoping.
- `src/services/mcp-tokens.service.ts`: has existing scope types and token management patterns that can be generalized or mirrored for API tokens.

### Established Patterns

- Public machine endpoints are routed through Cloudflare Worker vanity domains rather than asking clients to use raw Supabase URLs.
- Supabase Edge Functions use service-role clients for server-side data access and enforce their own application-level auth boundaries.
- MCP is one Edge Function with internal tool modules. REST should follow the same maintainable internal-module principle, but not the MCP protocol.
- Workspace entry joins are the canonical way to scope recordings to workspaces.
- Recording ID handling must stay UUID-safe and avoid legacy BIGINT coercion.

### Integration Points

- Add a new REST API Edge Function under `supabase/functions/`.
- Add `/v1/*` route resolution in `cloudflare/api-proxy/worker.ts`.
- Add or generalize API-token generation in SQL migrations and frontend services.
- Add a Developer/API settings surface or extend the current integration settings so users can create, copy once, view, and revoke API tokens.
- Replace or deprecate Obsidian-specific token/service/function code where the REST API makes it redundant.
- Add tests for auth source rejection, JSON envelopes, pagination, workspace/org scoping, and proxy route resolution.

</code_context>

<specifics>
## Specific Ideas

- The user explicitly confirmed the REST API exists for future use and so Obsidian can use it.
- The REST API should make the architecture simpler, not add a second permanent Obsidian-only API universe.
- The current Obsidian implementation has not been used yet, so compatibility should not block cleanup.
- Good first live proof after deployment is a `curl` against `https://api.callvaultai.com/v1/...` using a temporary API token, plus checks for missing token 401 and wrong-source token 403.

</specifics>

<deferred>
## Deferred Ideas

- Broad public write/admin API endpoints are deferred unless explicitly promoted later.
- Supabase raw `/rest/v1` exposure is not part of the product API direction.
- Keeping `obsidian-sync` for backward compatibility is deferred/rejected unless planning discovers an untracked real user or deployment dependency.
- Rate limiting, SDKs, OpenAPI publishing, and full developer docs can be planned as follow-ups unless the minimal API docs/examples are needed to verify Phase 06.2.

</deferred>
