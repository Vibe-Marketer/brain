# Phase 06.3: Obsidian Sync Improvements - Context

**Gathered:** 2026-06-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 06.3 captures the shipped Obsidian export behavior that was added without formal GSD plan tracking: users can download their vault as an Obsidian-compatible ZIP with one markdown file per call, YAML front matter, workspace-based folders, and transcript body content.

This phase is context recovery and scope-locking for the shipped feature. It does not add a new Obsidian plugin, does not restore the removed `obsidian-sync` Edge Function, does not create a permanent Obsidian-specific token universe, and does not rename `legacy_recording_id`; those concerns belong to Phase 06.2, Phase 06.3.1, or Phase 06.3.2 as noted below.

</domain>

<decisions>
## Implementation Decisions

### Export Surface and User Flow

- **D-01:** Treat Phase 06.3 as already shipped. This context file exists to make downstream planning understand what landed and what still needs cleanup/proof, not to reopen product scope for the base export.
- **D-02:** The primary full-vault Obsidian export surface is the Settings API Tokens section, where users can click `Download all calls` under `Export vault`. This export uses the authenticated browser session and does not require the user to generate or paste an API token.
- **D-03:** The API Tokens section remains the right home because Obsidian is now framed as an integration that uses the canonical CallVault REST API over time, while still offering a one-click browser ZIP export for immediate vault portability.
- **D-04:** `SmartExportDialog` may keep its selected-call `Obsidian Vault` organization mode as a secondary export path. It is not the canonical full-vault export entry point and should not conflict with the API Tokens section copy.
- **D-05:** The user-facing copy should emphasize ownership and portability: plug-and-play Obsidian ZIP, drop into the vault root, `CallVault/` folder created automatically. Avoid "AI-powered" framing.
- **D-06:** Per-call Obsidian export from an individual call/detail surface is not Phase 06.3. It belongs to inserted follow-up Phase 06.3.1.

### Markdown and Vault Format

- **D-07:** The canonical ZIP structure is `CallVault/{organization}/{workspace}/{date}-{title}.md`, with path segments sanitized for filesystem compatibility and duplicate filenames suffixed deterministically.
- **D-08:** Each markdown file should contain YAML front matter followed by a readable call note body. Required front matter fields for this phase are: `callvault_id`, `type`, `date`, `date_time`, `duration_min`, `organization`, `workspace`, `vault_path`, `word_count`, `participants`, `tags`, `has_transcript`, `share_url` when available, and `synced_at`.
- **D-09:** Tags should include `callvault`, a workspace tag, and a year/month tag when a date is available.
- **D-10:** Participants should be Obsidian wikilinks where names are known. The current participant source is `recorded_by_name` plus `calendar_invitees`; deeper participant-table enrichment is a future quality improvement unless planning proves it is cheap and necessary.
- **D-11:** Transcript body formatting should preserve stored transcript text rather than inventing speaker/timestamp structure that is not present. If stored transcript lines already include speaker attribution and timestamps, the export should preserve them. If not, do not synthesize false precision.
- **D-12:** Markdown body should include `# {title}`, date, duration when known, workspace, participants when known, optional summary, and a `## Transcript` section. Missing transcripts render an explicit `Transcript not available.` message.

### Data Source and Metadata Correctness

- **D-13:** Browser full-vault export fetches org recordings through the frontend service layer, not directly from a component. Keep service + hook/component separation intact; components call hooks/services only through established patterns.
- **D-14:** The export fetch should stay org-scoped and RLS-backed by the authenticated user session. It should map workspace names through `workspace_entries`, because workspace placement is the meaningful Obsidian folder boundary.
- **D-15:** Future cleanup should remove `any` casts from `fetchAllCallsForObsidianExport()` and use typed rows. This is cleanup, not new product scope.
- **D-16:** Future cleanup should use the canonical share/source URL helper pattern (`resolveShareUrl()` where applicable) rather than hand-selecting only `source_metadata.fathom_url` and `source_metadata.zoom_share_url`.
- **D-17:** The export must prefer canonical UUID identity in front matter (`recordings.id` / `canonical_uuid`) and avoid creating new dependencies on numeric Fathom IDs. Phase 06.3.2 owns the `legacy_recording_id` to `fathom_provider_id` rename.
- **D-18:** There must be no product-level 500-record export ceiling. The export must support the user's full vault, with the known owner-scale case of at least 1,500 recordings.
- **D-19:** Full-vault scale proof must use realistic transcript-bearing records, not only empty metadata rows, because ZIP memory pressure is driven by transcript size.

### Backend and API Boundary

- **D-20:** `obsidian-sync` is not the canonical backend architecture. It should be gone. If any source, docs, deployment manifest, or route still exposes it, downstream agents should remove it or mark it explicitly deprecated as part of cleanup. Do not restore it for Phase 06.3.
- **D-21:** API tokens (`token_source = 'api'`) are the canonical credential model for external integrations, including any future Obsidian plugin sync.
- **D-22:** Obsidian-labeled tokens should be normal API tokens with a name such as "Obsidian Plugin", not a separate `token_source = 'obsidian'` path.
- **D-23:** Any future plugin sync should use `api.callvaultai.com/v1/*` routes from Phase 06.2. It should not call raw Supabase URLs, MCP endpoints, or a revived Obsidian-only function.
- **D-24:** The old migration `supabase/migrations/20260608120000_obsidian_sync_token_label.sql` remains historical database history and should not be edited. Active source/docs should point users toward API tokens and REST.

### Verification and Scale

- **D-25:** Verification for Phase 06.3 should include source-level checks that `exportToObsidian()` writes one `.md` file per included call, emits required front matter, sanitizes paths, handles duplicate titles, and creates `callvault-obsidian-{date}.zip`.
- **D-26:** Add or keep focused tests around YAML/front matter escaping, participant rendering, missing transcript handling, duplicate path suffixing, workspace exclusion, and source/share URL preservation.
- **D-27:** UI verification should prove the Settings export button enters an exporting state, handles empty vaults with `No calls to export`, and reports export failure without leaving the button stuck.
- **D-28:** Scale proof must cover at least 1,500 realistic transcript-bearing calls. If a single in-browser ZIP is too memory-heavy, planning must introduce a user-safe full-export strategy such as batching, streaming/server-side generation, or multiple ZIP parts. It is not acceptable to silently cap at 500 or export only a subset of the user's vault.
- **D-29:** Manual ZIP inspection is acceptable as a final smoke only after automated tests cover the deterministic pieces. It should not be the sole proof.

### the agent's Discretion

The user explicitly said to run with assumptions. Downstream agents may choose the exact test shape, fixture sizes, extraction points, and cleanup order, provided they preserve the decisions above and do not expand the phase into the follow-up phases.

## Existing Code Insights

### Reusable Assets

- `exportToObsidian(calls, orgName, excludedWorkspaceNames)` in `src/lib/export-utils.ts`: creates the Obsidian ZIP, sanitizes path segments, suffixes duplicate paths, builds YAML front matter, and saves `callvault-obsidian-{date}.zip`.
- `fetchAllCallsForObsidianExport(orgId)` in `src/services/api-tokens.service.ts`: fetches org workspaces, maps `workspace_entries` to workspace names, fetches recordings, and maps them to `ExportableCall[]`.
- `ApiTokensSection` in `src/components/settings/ApiTokensSection.tsx`: provides the primary `Export vault` card and `Download all calls` action.
- `SmartExportDialog` in `src/components/SmartExportDialog.tsx`: provides a secondary `Obsidian Vault` selected-call export path with workspace exclusion controls.

### Established Patterns

- Service + hook/component separation is locked. Data fetching belongs in services/hooks, not directly in presentational component logic.
- Frontend icons use `@remixicon/react`; no Lucide or FontAwesome.
- Machine integrations should use API tokens and `api.callvaultai.com/v1/*`; MCP and raw Supabase URLs are not Obsidian sync surfaces.
- Recording ID code must preserve UUID-first behavior and route numeric/Fathom compatibility through established helper boundaries.

### Integration Points

- Settings > API Tokens: primary full-vault Obsidian ZIP export and API-token setup instructions.
- Smart Export dialog: selected-call Obsidian export for user-selected subsets.
- Future REST API/plugin sync: Phase 06.2 `callvault-api` routes and `token_source = 'api'` tokens.
- Future per-call export: inserted Phase 06.3.1.
- Future Fathom provider-ID rename: inserted Phase 06.3.2.

<specifics>
## Specific Ideas

- Treat the full-vault ZIP as a one-click portability feature. The user should not have to generate an API token for the browser download.
- "Full vault" means full vault, not the first 500 calls. The known owner-scale case is approximately 1,500 calls and must be supported.
- Keep the Obsidian folder structure predictable and inspectable: `CallVault/{org}/{workspace}/{date}-{slug}.md`.
- Preserve transcript text exactly when possible; do not fabricate timestamps or speaker attribution.
- Use automated tests for deterministic ZIP/markdown behavior and browser/manual inspection only as final smoke.

</specifics>
