# Phase 06.3: Obsidian Sync Improvements - Research

**Researched:** 2026-06-10
**Status:** Ready for planning

## Summary

Phase 06.3 is not green just because the current UI has a `Download all calls` button. The shipped implementation proves the basic Obsidian ZIP shape, but the corrected requirement is stronger: a full-vault export must handle at least 5,000 realistic transcript-bearing recordings without an arbitrary 500-record ceiling.

The biggest technical risk is row retrieval and memory, not the markdown format itself. The current `fetchAllCallsForObsidianExport()` calls `.select()` on `recordings` once, with no explicit pagination. Supabase/PostgREST installations commonly enforce a maximum row count, so an unpaged query is not a reliable full-vault export strategy. The plan must page through workspaces, workspace entries, and recordings until exhausted, then generate files from the complete set.

The old `obsidian-sync` source files are already deleted by Phase 06.2. Remaining active concerns are: historical SQL still contains `generate_obsidian_token`; a new uncommitted migration exists to drop that dead token path; active docs/source must not reintroduce `/obsidian-sync`; and the export utility needs focused tests.

## Current State

### Primary Export Surface

- `src/components/settings/ApiTokensSection.tsx` owns the primary full-vault export button: `Export vault` -> `Download all calls`.
- The button calls `fetchAllCallsForObsidianExport(defaultOrgId)` and then `exportToObsidian(calls, orgName)`.
- The export uses the logged-in browser session, not an API token. That matches the one-click portability requirement.

### Secondary Export Surface

- `src/components/SmartExportDialog.tsx` has an `Obsidian Vault` organization mode for selected calls.
- It enriches selected calls with transcripts, lets users exclude workspaces, then calls `exportToObsidian()`.
- This can remain a selected-subset path, but it is not the canonical full-vault path.

### Data Fetching

- `src/services/api-tokens.service.ts` currently fetches all workspaces for an org, then all workspace entries for those workspaces, then all recordings for the org.
- The service uses `any` casts for workspace entries, recordings, and metadata.
- The recording select currently includes `legacy_recording_id`. Phase 06.3.2 owns the later rename; Phase 06.3 should not expand into that rename, but it should avoid increasing numeric-ID dependency.
- The service reads share URLs from `source_metadata.fathom_url` and `source_metadata.zoom_share_url` rather than the canonical helper pattern.

### ZIP/Markdown Generation

- `src/lib/export-utils.ts` contains `exportToObsidian()`, which uses `JSZip`, writes `CallVault/{org}/{workspace}/{date}-{slug}.md`, builds YAML front matter, suffixes duplicate file paths, and saves `callvault-obsidian-{date}.zip`.
- The core builder functions are not exported, so unit tests must either test through JSZip/saveAs mocks or the implementation should expose testable internal helpers.
- Existing generic markdown helper `transcriptToMarkdown()` parses a timestamped speaker pattern but is not used by `exportToObsidian()`. This is acceptable: Phase 06.3 context says preserve stored transcript text and do not fabricate timestamps.

### Obsidian-Specific Backend Cleanup

- Phase 06.2 summary and verification show these source files were deleted: `src/services/obsidian-tokens.service.ts`, `src/hooks/useObsidianTokens.ts`, `src/components/settings/ObsidianConnectorSection.tsx`, and `supabase/functions/obsidian-sync/index.ts`.
- A current working-tree migration `supabase/migrations/20260610013718_drop_obsidian_token_type.sql` exists and appears to drop `generate_obsidian_token` dead code. Planning must account for it without overwriting it.
- Historical migrations are immutable; do not edit `supabase/migrations/20260608120000_obsidian_sync_token_label.sql`.

## Recommended Technical Direction

### 1. Fix Full-Vault Retrieval First

Add explicit pagination to the browser service. Use a small helper such as `fetchAllRows()` or dedicated loops with `.range(from, to)` and a page size around 1,000. Fetch until a page returns fewer than page size. Apply this to:

- `workspaces` for the org
- `workspace_entries` for all workspace IDs, chunking `.in()` inputs if needed
- `recordings` for the org, ordered by `recording_start_time`

This removes dependence on Supabase default row limits and is mandatory for 5,000-call export.

### 2. Make Export Builders Testable

Expose or factor testable functions in `src/lib/export-utils.ts` without changing the public user-facing API:

- path sanitization and slug generation
- Obsidian front matter construction
- Obsidian markdown note construction
- ZIP assembly

This lets tests assert one file per call, duplicate path suffixes, YAML escaping, missing transcript behavior, participant rendering, and workspace tags.

### 3. Treat 5,000 Calls as a Real Scale Gate

A 5,000-call fixture should include realistic transcript sizes. Empty records are not a valid proof. A good automated fixture can generate 5,000 calls with deterministic titles, workspaces, participants, summaries, and transcript bodies of a configurable length. The test should assert:

- `zip.file()` called 5,000 times, or the generated zip contains 5,000 markdown entries if the test can afford it
- export does not truncate at 500 or 1,000
- memory-safe strategy is used if plain JSZip cannot complete within a reasonable time

If JSZip with one browser blob is too memory-heavy, implement a user-safe fallback rather than reducing scope:

- multiple ZIP parts with clear filenames, or
- a server-side/streaming export endpoint, or
- a chunked browser export with progress and deterministic part boundaries

For this repo's current dependencies, the lowest-risk first implementation is paged fetch + JSZip + scale benchmark/test. Only introduce new ZIP streaming dependencies if the 5,000-call proof fails.

### 4. Preserve REST/API Direction

Do not restore `obsidian-sync`. Future plugin sync should use Phase 06.2's REST API and `token_source = 'api'`. Phase 06.3 may verify that active source/docs do not present `/obsidian-sync` or Obsidian token generation as the current path.

## Risks

- **Silent truncation:** Unpaged Supabase queries may return only a capped subset. This is the main risk against "full vault."
- **Browser memory pressure:** JSZip can hold a large in-memory representation before saving. 5,000 transcript-bearing calls may require chunking or a stronger export strategy.
- **YAML validity:** Title, workspace, organization, and participant names need escaping beyond basic quote replacement.
- **URL drift:** Hand-picked metadata URL keys can miss valid source URLs. Use the canonical share URL helper pattern where possible.
- **Phase collision:** Phase 06.3.2 will rename `legacy_recording_id`; Phase 06.3 plans should not perform that rename but should avoid deepening dependence on the old name.
- **Unrelated working tree changes:** Current repo has unrelated source modifications and untracked planning/migration files. Execution must read current files and avoid reverting user work.
