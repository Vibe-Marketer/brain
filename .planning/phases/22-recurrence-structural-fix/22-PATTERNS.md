**Rollup RPC pattern** (lines 147-181, 223-274):
```sql
CREATE OR REPLACE FUNCTION public.rollup_autopilot_category_trust()
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $function$
BEGIN
  WITH eligible_runs AS (
    SELECT rr.id, rr.ticket_id, rr.fix_category AS category, rr.survival_status
    FROM public.runner_runs rr
    WHERE rr.fix_category IS NOT NULL
      AND rr.merged_at IS NOT NULL
      AND rr.survival_due_at <= now()
      AND rr.survival_due_at >= now() - interval '30 days'
  ),
  rollups AS (
    SELECT er.category, COUNT(*)::integer AS completed_fixes_30d
    FROM eligible_runs er
    GROUP BY er.category
  ),
  upserted AS (
    INSERT INTO public.autopilot_category_trust (...)
    SELECT ...
    ON CONFLICT (category) DO UPDATE SET
      completed_fixes_30d = EXCLUDED.completed_fixes_30d,
      last_rollup_at = EXCLUDED.last_rollup_at,
      updated_at = now()
  )
```

Use this CTE -> grouped rollups -> `INSERT ... ON CONFLICT ... DO UPDATE` shape for `rollup_ticket_classes()`. For Phase 22, the base CTE should read `tickets` where `status='resolved'`, classify by `source`, error class, and source-namespaced fingerprint root, then calculate both `resolved_count_30d` and `occurrence_count_30d`.

```typescript
function normalizeCategoryPart(input: unknown, fallback: string): string {
  const raw = typeof input === "string" && input.trim().length > 0 ? input.trim() : fallback;
  const normalized = raw.toLowerCase().replace(/[^a-z0-9_:-]+/g, "_").replace(/^_+|_+$/g, "");
  return normalized || fallback;
}

function errorClassFromContext(context: unknown): string {
  const sentry = objectValue(context, "sentry");
  const candidates = [
    objectValue(context, "error_class"),
    objectValue(context, "errorClass"),
    objectValue(context, "error_type"),
    objectValue(context, "exception_type"),
    objectValue(sentry, "error_class"),
    objectValue(sentry, "exception_type"),
    objectValue(sentry, "type"),
  ];
  return normalizeCategoryPart(candidates.find((value) => typeof value === "string"), "unknown");
}

export function buildFixCategory(ticket: { source?: string | null; context?: unknown }): string {
  return `source:${normalizeCategoryPart(ticket.source, "unknown")}:error:${errorClassFromContext(ticket.context)}`;
}
```

## Shared Patterns

### Database/RPC Security

Use `SECURITY DEFINER SET search_path = public, pg_temp` for RPCs. Admin-facing read RPCs must check `public.has_role(auth.uid(), 'ADMIN')`. Service-role rollups/escalation RPCs should be revoked from `PUBLIC`, `anon`, and `authenticated`, then granted only to `service_role`, matching the Phase 19 restriction test.

### Occurrence Accounting

Count both ticket rows and deduped occurrence counts. Sentry/QA ingestion already uses `occurrence_count` and `last_seen_at`; recurrence threshold should use occurrence count for deduped repeats and also expose resolved ticket row count so AdminTab can distinguish "three tickets" from "one fingerprint seen three times."

### Structural Fix Routing

Structural fixes are class-level work, not per-instance bug fixes. They may be represented as `tickets.type='task'`, `source='internal'`, `status='escalated'`, with `context.structural_fix`, and queued as a tier-2 digest. They must never emit or route as `auto_fix`, even when the underlying source/error category has auto trust.

### Admin UI Data Access

Follow service + hook separation: service calls `supabase.rpc()`, hook wraps with TanStack Query, component renders `data/isLoading/error`. Do not compute recurrence metrics in React and do not query Supabase directly from `DashboardSection.tsx`.

### Plain-English Surface

AdminTab and ticket detail surfaces must use humanizers from `src/lib/ticket-display.ts` or local helper functions. Avoid raw enum/class-key/context output in user-visible labels.

### Tests

Use static migration tests for SQL shape and permissions, service unit tests for RPC mapping, and real Supabase integration tests for rollup/idempotency/RLS. Integration tests must skip cleanly when test DB env is absent and must never mock Supabase.
