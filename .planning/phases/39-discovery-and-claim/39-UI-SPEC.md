# Phase 39 — UI Design Contract

> Visual and interaction contract for verified-email event discovery, participation invitations, secure claims, and claimed-email management. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Source and Decision Precedence

This contract applies all locked decisions D-01 through D-23 in `39-CONTEXT.md`. The verified-email boundary, Phase 38 recording-access rules, and existing organization-scoped people RPC contracts are fixed. Visual details in this file may clarify those decisions but may not widen access.

Four authorization facts remain visibly and behaviorally separate:

1. A user proved control of an email address.
2. That verified email matches confirmed participation in an event.
3. The user may see the event's privacy-safe existence projection.
4. A Phase 38 policy or approved request allows the user to read a recording.

Claiming participation completes the first two facts and enables the third. It never implies the fourth. The UI must not use language such as **“recording claimed,” “recording unlocked,” “access granted,”** or **“your recording”** after a claim unless a separate Phase 38 result actually grants content access.

No pre-authentication claim surface may preview a private event title, owner, provider, date, participant, recording count, transcript, summary, or thumbnail. Existing organization-scoped People surfaces remain unchanged.

---

## Visual Hierarchy

1. The persistent Settings result **“We found N events”** is the completion signal after an email is verified or claimed.
2. The dedicated Events page prioritizes cards with a current user action, followed by events with readable content, then events waiting on an existing request. Each group is newest first.
3. Event date/time and the current user's verified-email connection are the primary safe identity of an event. A real title appears only when returned from a recording the user can already read.
4. Anonymous restricted copies are visually quieter than readable recordings and use ordinal labels only.
5. In the Participants section, invitation status is secondary metadata beside the canonical participant row. **Invite to claim** is the only primary row action.
6. Claim processing is calm and transactional. No confetti, celebratory animation, private preview, or marketing interstitial appears between authentication and Events.

Vibe orange remains a structural accent for page wayfinding, active navigation, focus, and approved links. It is not a claim-success color, access-status color, or full-card fill.

## Surface 1 — Account Settings Discovery and Verified Emails

### Placement

- Extend the existing **Verified Emails** section in `AccountTab.tsx`; do not create a second identity settings page.
- Place the discovery result immediately after the primary/alias list and before **Add email**.
- Keep the existing email-code flow for manually added aliases. A participation claim link itself proves the invited email and must not ask for the existing six-digit code again.

### Persistent discovery result

Render a neutral `bg-muted/60` callout with a Remix calendar-event icon, result text, and action:

- Zero: **“We found 0 events”**
- One: **“We found 1 event”**
- Many: **“We found [N] events”**
- Action: **“View events”**

The number uses `tabular-nums`. **View events** navigates to `/events` even when the count is zero so the user can reach the page's explanatory empty state. This is a persistent account result, not a toast. A successful email verification or claim may also show a one-time toast, but the callout remains the durable status.

The count is one server-provided distinct-event count across the confirmed primary email and all active verified aliases. The client must not add per-email counts because one event may match more than one owned address.

### Loading and failure

- While the count loads, render a fixed-height skeleton for the number and action. Never flash **“We found 0 events”** before the real result arrives.
- Count failure heading: **“We couldn't check for matching events.”**
- Failure action: **“Try again”** using a hollow button.
- Keep the verified-email list usable when only the count fails.

### Verified-email rows

Each row contains, in order:

1. Verified Remix icon.
2. Full email address, because the signed-in account owner is viewing their own Settings.
3. Neutral status text: **“Primary”** or **“Verified”**.
4. For non-primary aliases only, a quiet **“Disconnect email”** action.

The primary account email cannot be disconnected in this surface. A claimed alias behaves like any other verified alias after claim; do not create a permanent special class that changes its authorization semantics.

### Disconnect confirmation

Disconnect uses the existing `AlertDialog`:

- Title: **“Disconnect [email]?”**
- Description: **“Events connected only through this email will no longer appear, and future matches will stop. Original participant records will not be changed.”**
- Cancel: **“Keep email connected”**
- Confirm, destructive variant: **“Disconnect email”**

Do not optimistically remove authorization-sensitive data. Disable only the affected row while the server completes the mutation. On success, remove the alias, invalidate alias/discovery/access/notification caches, and announce:

- Success toast: **“[email] disconnected.”**
- Failure toast: **“Couldn't disconnect this email. Nothing changed. Try again.”**

After success, the result callout and open Events page must refetch immediately. Cards and notification actions whose only authority came from the disconnected alias disappear without a page reload.

## Surface 2 — Dedicated Events Page

### Route and navigation

- Protected route: `/events`.
- Add **EVENTS** to the main app navigation immediately after **CALLS**.
- Navigation description: **“Meetings connected to you”**.
- Inactive icon: `RiCalendarEventLine`; active icon: `RiCalendarEventFill`.
- Active styling follows the existing `SelectionButton` / sidebar pattern. Do not add a separate navigation style.
- Page title: **“EVENTS”** using the authenticated page-title wayfinding treatment.
- Page subtitle: **“Events connected to your verified emails.”**

The Settings **View events** action and a completed claim both navigate to this same route. Claim completion uses route replacement so the claim URL is not restored by the browser Back button.

### Grouping and ordering

The server returns a stable priority and cursor. The frontend preserves this order and does not reclassify based on hidden recording data.

1. **Needs your action** — at least one anonymous restricted copy currently allows **Request access**.
2. **Available to you** — at least one readable recording exists and no higher-priority action is present.
3. **Waiting for access** — no current action is available because all relevant requests are pending or in cooldown.

Within every group, order by event start time newest first, with event ID only as a stable tie-breaker. Omit a group heading when that group is empty. This third waiting group prevents a pending request from being mislabeled as content that is already available while preserving the locked action-first and available-next ordering.

Use cursor pagination whose cursor includes priority, event time, and stable ID. Action: **“Load more events”**. Loading more appends without reordering cards already on screen. After a mutation changes priority, refetch the ordered list and retain focus on the triggering row or its resulting status.

### Event card anatomy

Use a single-column card list in the main pane. A card is a semantic article, not one giant clickable control, because it can contain multiple recording actions.

Each card may contain only this server-projected information:

1. **Safe heading**
   - If a readable recording supplies a permitted title, show that title.
   - Otherwise use **“Event on [localized date]”**.
2. **Event date and time** using a semantic `<time>` element and the user's locale/timezone.
3. **Connection**: **“Connected through [verified email]”**. When more than one owned email matched, show **“Connected through [N] verified emails”** with no participant roster.
4. **Readable recordings**: normal permitted title/source metadata and **“Open recording”** for each recording the user can already access.
5. **Restricted copy summary**: **“[N] other recording(s)”** with anonymous ordinal rows such as **“Recording 1”**.
6. **Request state/action** from Phase 38: **“Request access,” “Sending…,” “Request sent,”** or **“Available [date]”**.

Use existing neutral bordered row styling inside the card for recording rows. Readable rows may use their normal source treatment because permission was already established. Anonymous rows must never contain owner, provider, private title, participant count/list, organization, workspace, thumbnail, transcript, summary, URL, duration, or raw recording ID.

Do not place protected data in hidden DOM nodes, accessible labels, test IDs, analytics labels, client logs, tooltip content, or CSS-hidden fields. Redaction happens in the server projection before transport.

### Request access behavior

- Reuse Phase 38's one-click request interaction and state copy.
- Visible CTA: **“Request access”**.
- Accessible label: **“Request access to recording [ordinal] from [event date]”**.
- During mutation, disable only the selected anonymous row and show **“Sending…”**.
- Success toast: **“Access request sent. The recording owner has been notified.”**
- Failure toast: **“Couldn't send your request. Try again.”**
- If the server reports an existing request, render that existing status rather than an error or duplicate request.
- Approval promotes the recording to the readable treatment only after the server confirms access.

### Empty state

When the server returns no events across all active verified emails, center the standard empty-state treatment:

- Icon: `RiCalendarEventLine` in a `bg-muted/60` container.
- Heading: **“No events found yet”**
- Body: **“We'll show events here when they match one of your verified emails.”**
- Action: **“Manage verified emails”** linking to Account Settings.

Do not mention organizations, recording owners, import providers, or possible hidden matches.

### Loading and error states

- Initial load: three event-card skeletons matching the real card's date, connection, row, and action geometry. Do not render group headings until data establishes a group.
- Pagination load: keep existing cards and render one trailing skeleton; do not replace the page.
- Page error heading: **“We couldn't load your events.”**
- Error body: **“Check your connection and try again.”**
- Error action: **“Try again”**.
- If access is revoked or an alias is disconnected while a card is open, remove the unauthorized card after refetch and show **“This event is no longer available.”** Do not explain which policy or account caused the change.

## Surface 3 — Recording Owner Participation Invitations

### Attachment and eligibility

- Add invitation controls to the recording's existing **Participants** section in `CallParticipantsTab`.
- Only the recording owner receives invitation eligibility and invitation actions from the server.
- Render **Invite to claim** only beside a canonical participant row that has a server-validated participant ID, an existing participant email, and current eligibility.
- Transcript-only merged speakers, anonymous labels, the recording owner, already-claimed participants, and rows without an email receive no disabled control or eligibility hint.
- Never add a free-form address field, multi-select checkbox, bulk invite action, or **Invite everyone** control.

The participant name/email treatment stays primary. Invitation controls appear at the trailing edge on desktop and beneath the participant metadata on mobile.

### Before sending

An eligible row contains:

- Primary row action: **“Invite to claim”**.
- Labeled `Switch`, off by default: **“Send one reminder”**.
- Accessible description: **“Send one automatic reminder before this invitation expires.”**

The switch is per participant invitation and resets to off for every new or resent invitation. Keeping it off sends no automatic reminder. The control does not create an account-wide reminder default.

Sending is one participant at a time. During send, disable the action and switch on that row only and change the action to **“Sending…”**. Other eligible rows remain available.

### Sent and terminal states

Every invitation renders a text status and absolute sent date. Status must not rely on color alone.

| State | Visible contract |
|-------|------------------|
| Active, no reminder | Badge **“Invitation sent”** · **“Sent [date]”** · **“Resend available [date]”** |
| Active, reminder pending | Badge **“Invitation sent”** · **“Sent [date]”** · **“Reminder scheduled [date]”** · link **“Cancel reminder”** |
| Reminder sent | Badge **“Reminder sent”** · **“Sent [date]”** · **“Reminded [date]”** |
| Claimed | Success badge **“Claimed”** · **“Claimed [date]”**; no resend action |
| Expired, at least seven days old | Neutral badge **“Expired”** · **“Sent [date]”** · action **“Resend invite”** |
| Revoked or superseded | Neutral badge **“No active invitation”**; render current server-allowed action only |

Manual resend appears only when the server says the prior invitation is at least seven days old. The client may display the date but may not authorize resend from its own clock. **Resend invite** immediately creates a fresh invitation and fresh seven-day link; it never revives the old token.

Canceling a scheduled reminder uses a quiet link action without a confirmation dialog. On success show **“Reminder canceled.”** On failure retain the scheduled state and show **“Couldn't cancel the reminder. Try again.”**

### Invitation feedback

- Initial send success: **“Invitation sent to [participant name].”**
- Initial send failure: **“Couldn't send this invitation. Try again.”**
- Resend success: **“A new invitation was sent to [participant name].”**
- Resend failure: **“Couldn't resend this invitation. Try again.”**
- Concurrent/stale state: refetch the row and show **“This invitation changed. The latest status is shown.”**

### Invitation email copy

The initial email and optional one-time reminder must not preview private event or recording details before authentication.

- Initial subject: **“Claim your participation in CallVault”**
- Initial heading: **“Connect your email to your events”**
- Initial body: **“You were invited to verify this email and find events connected to you in CallVault.”**
- Initial CTA: **“Claim participation”**
- Reminder subject: **“Reminder: claim your participation in CallVault”**
- Reminder CTA: **“Claim participation”**
- Expiry note: **“This link expires on [date].”**

No email includes a private title, owner, provider, participant roster, transcript, summary, recording URL, or recording count. The reminder uses the same still-active link and is scheduled before its expiry.

## Surface 4 — Secure Claim Entry and Authentication Return

### Route and token handling

- Public entry route: `/claim-participation` with the opaque token accepted once from the email URL.
- Validate token shape before storage, place it in the dedicated pending-claim session key, and immediately remove it from the visible URL with history replacement.
- Never write the token to logs, analytics, query caches, error text, DOM attributes, or local storage.
- The protected completion destination is `/events`.

### Signed-out or new user

After capturing a valid-shaped token, show a privacy-safe claim page with no event preview:

- Heading: **“Claim your participation”**
- Body: **“Sign in or create an account to verify this email and find events connected to you.”**
- Primary CTA: **“Continue to CallVault”**

The CTA enters the existing login/signup experience with the pending claim preserved. Password login, password signup, OAuth, callback, and root bootstrap must all restore the same pending claim. Authentication success automatically begins claim completion; the user does not need to reopen the email or click a second verification action.

### Signed in to the intended account

Show a noninteractive processing state:

- Heading: **“Verifying your email…”**
- Body: **“Keep this page open while we connect your events.”**

On success, remove the pending token, replace the route with `/events`, focus the Events page heading, and show:

- Success toast, zero: **“Email verified. No matching events were found yet.”**
- Success toast, one: **“Email verified. We found 1 event.”**
- Success toast, many: **“Email verified. We found [N] events.”**

The toast describes event discovery only. It must not say content access was granted.

### Signed in with a different primary email

The signed-in user may attach the invited email to the current account without a second code. Show only a masked invited address until the authenticated server response authorizes the prompt.

- Heading: **“Add this email to your account?”**
- Body: **“You're signed in as [current email]. Add [masked invited email] as a verified email to find events connected to it.”**
- Primary CTA: **“Add email and continue”**
- Secondary CTA: **“Use another account”**

**Add email and continue** atomically attaches the verified alias and completes the claim. **Use another account** preserves the pending claim while returning to authentication; it does not consume the token. Never display another account's identity or state.

### Generic terminal state

Missing, malformed, expired, already-used, revoked, superseded, and conflicting-account links share one public result:

- Heading: **“This claim link is no longer available”**
- Body: **“Ask the recording owner to send a new invitation, or sign in to view events already connected to your account.”**
- Primary CTA: **“Sign in”**

Do not vary status code text, heading, icon, detail, or action based on the internal reason. Clear the pending token after a terminal result.

### Retryable failure

A network or temporary server failure does not consume or clear the pending claim:

- Heading: **“We couldn't finish this claim.”**
- Body: **“Check your connection and try again.”**
- Primary CTA: **“Try again”**

Disable **Try again** while retrying. Parallel clicks must not issue parallel consume requests.

## Surface 5 — Future-Match In-App Notification

Extend the existing `user_notifications`, `useNotifications`, and `NotificationBell` surface. Do not add a second notification center, toast-only notification, email digest, or recurring email alert.

- Title: **“New event found”**
- Body: **“We found a new event connected to one of your verified emails.”**
- Action: **“View event →”**

The notification contains no private title, owner, provider, participant roster, transcript, summary, or restricted recording count. Activating it marks the notification read and opens `/events` focused on the authorized event card. If authorization no longer exists, remove or neutralize the action and show **“This event is no longer available.”**

Current matches established when an email is first verified or claimed do not generate a historical notification burst. Only later matches create one in-app notification per user/event.

## State and Concurrency Contract

| Situation | Required behavior |
|-----------|-------------------|
| Count and list resolve at different times | Each surface owns its skeleton; neither invents zero or stale counts. |
| Claim succeeds while Events is already cached | Invalidate discovery, aliases, notifications, access, and affected call-list caches before presenting the settled Events result. |
| Disconnect occurs in another tab | Refetch on focus; remove unauthorized cards and neutralize stale notification links. |
| Two invitation sends race | Server state wins; render one active invitation and show the latest status. |
| Old link opened after resend | Render the generic unavailable state; never identify the newer invitation. |
| Claim consume retried after success | Route to Events from authenticated settled state; never attach twice or show a token-specific diagnostic. |
| Request access already exists | Render pending/cooldown status instead of reporting failure. |
| Event has readable and restricted copies | Show permitted readable details plus anonymous restricted rows in the same card; never infer shared access. |
| Event loses all current-email authority | Remove it on refetch and show only the generic no-longer-available message. |

## Accessibility Contract

- Use one `h1` for **EVENTS**, `h2` for event groups, and an accessible heading for each event card. Group headings are omitted with empty groups.
- Render event cards as a semantic list of articles. Do not nest buttons or links inside a card-wide interactive control.
- Every icon is decorative with `aria-hidden="true"` unless it is the sole control content. Icon-only controls require an explicit `aria-label`.
- Dates use `<time dateTime="…">`; numeric counts use `tabular-nums`.
- Statuses always include text. Do not communicate requested, claimed, expired, scheduled, unavailable, or readable state through color or icon alone.
- The reminder `Switch` has a visible label and accessible description tied to the same participant row.
- Invitation actions use accessible names such as **“Invite [participant name] to claim participation”** while visible copy remains **“Invite to claim.”**
- Anonymous request controls use the ordinal and event date in their accessible name without including restricted data.
- Loading skeleton containers use `aria-busy="true"`; skeleton shapes themselves are hidden from assistive technology.
- Mutation success uses a polite live region. Blocking failure copy uses `role="alert"`.
- `AlertDialog` traps focus, Escape cancels, and focus returns to the initiating Disconnect control.
- Claim processing moves focus only after a route/state transition, never on every loading render. Successful completion focuses the Events heading.
- All controls retain the existing vibe-orange focus-visible ring. Touch targets reach 44px on mobile.
- Respect `prefers-reduced-motion`; state changes remain understandable with motion removed.

## Motion

- Use existing route, shell, Radix dialog, and list transition behavior. Do not introduce a phase-specific timing curve.
- If card reordering after a request uses animation, use `motion/react` with the repository spring `{ type: 'spring', stiffness: 260, damping: 28 }` and preserve focus.
- Claim success uses route replacement and a toast only. No celebration or progress animation beyond the existing spinner/skeleton.
- Reduced-motion mode removes reordering/cross-fade motion while preserving final position and status.

## Privacy-Safe Rendering Checklist

- [ ] Unauthenticated claim page contains no event or recording preview.
- [ ] Restricted fields never enter the Events network payload.
- [ ] Event card exposes only the current user's connection, never a roster or participant count.
- [ ] Anonymous copies use ordinal labels and no stable visible identifiers.
- [ ] Invitation eligibility comes from the server and only canonical participant rows can be invited.
- [ ] Generic claim terminal copy is identical across expired, used, revoked, superseded, unknown, and conflict states.
- [ ] Disconnect removes derived visibility without deleting or rewriting participant evidence.
- [ ] Future-match notifications contain no private recording detail and are in-app only.
- [ ] Claim and invitation tokens never appear in logs, analytics, DOM attributes, or post-capture URLs.
