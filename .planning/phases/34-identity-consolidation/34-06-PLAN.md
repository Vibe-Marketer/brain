<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| React client -> request/confirm edge functions | The UI passes user-entered email + code; the functions (Plan 03) authenticate, validate, rate-limit, and enforce the attempt cap — the client enforces nothing security-critical |
| React client -> identity_aliases list read | Owner-scoped RLS returns only the caller's own verified emails; the client cannot enumerate other users' aliases |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-06-01 | Spoofing | client trying to "verify" without the emailed code | mitigate | All verification authority is server-side (Plan 03's confirm function: hash compare, expiry, attempt cap). The UI cannot mark an email verified on its own; it only relays email + code. |
| T-34-06-02 | Information Disclosure | listing another user's verified emails | mitigate | listVerifiedEmails relies on identity_aliases owner-scoped RLS (Plan 02) — a client JWT sees only its own owned identity's aliases. |
| T-34-06-03 | Denial of Service | user spamming "Send code" | mitigate | The request endpoint is per-user rate-limited (Plan 03); the UI should also disable the button briefly after send and surface the 429 toast, but the server is the real limiter. |
| T-34-06-04 | Information Disclosure | showing the raw code or a sensitive error | mitigate | The code is never returned by the request function; the UI collects it from the user's inbox. Error toasts are generic (bad/expired code) and do not distinguish "no such pending row" from "wrong code" (Plan 03 already blurs these). |
| T-34-06-SC | Tampering | npm/pip/cargo installs | accept | No package installs — all UI primitives already present (34-RESEARCH.md Package Legitimacy Audit: N/A). |
</threat_model>
