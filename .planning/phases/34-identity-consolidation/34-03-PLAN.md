<objective>
Build IDENT-03's email-ownership proof as a small custom hashed-OTP flow that reuses this codebase's existing infrastructure — the Resend HTTP integration (from send-org-invite) and the authenticateRequest JWT helper — WITHOUT touching Supabase Auth. This is the corrected Grey Area 1 mechanism: Supabase Auth is one-email-per-account, so `auth.updateUser({email})` would replace the login email rather than add one. Instead a pending-OTP table + two edge functions let a signed-in user prove they own a second email, which is then recorded as a verified `identity_aliases` row so calls under any of their verified emails resolve to one identity.

Purpose: Deliver the "attach multiple owned, verified emails" capability (IDENT-03) securely — CSPRNG code, hashed at rest, short expiry, hard attempt cap, request rate limit — reusing established patterns rather than fighting Supabase Auth's single-email model or standing up a second email provider.
Output: One OTP table (applied to TEST), two edge functions, shared OTP helpers with unit tests, an integration test proving the happy path + expiry + brute-force guard + client-deny RLS. Function deploy to prod is gated in Plan 07.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> request/confirm edge functions | Untrusted input (email, code) crosses here; both functions authenticateRequest first and Zod-validate |
| edge function (service-role) -> identity_alias_verifications | Trusted writer of the pending hash; the client can never read this table (client-deny RLS) |
| edge function -> Resend (api.resend.com) | Outbound email with the plaintext code; the code exists in plaintext only in transit + the recipient's inbox, never at rest |
| confirm -> identities/identity_aliases | Service-role write that claims an identity + records a verified email |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-03-01 | Spoofing | OTP brute-force (1,000,000 combos) | mitigate | 6-digit CSPRNG code (crypto.getRandomValues, never Math.random), SHA-256-hashed at rest, 10-min expiry, hard 5-attempt cap that invalidates the pending row. Proven by the attempt-cap integration test. HIGH severity. |
| T-34-03-02 | Denial of Service | email-bombing the request endpoint | mitigate | Per-user request rate limit (RateLimiter pattern from supabase/CLAUDE.md) on request-email-alias-verification, plus the UNIQUE(user_id, email) upsert coalescing repeated requests for the same address. |
| T-34-03-03 | Information Disclosure | plaintext code leaking via a client-readable row or the response | mitigate | Store only the SHA-256 hash; identity_alias_verifications is service-role-only (client-deny RLS, proven in rls-regression); neither function returns the code in its response body. |
| T-34-03-04 | Elevation of Privilege | verifying an email hijacks or duplicates a Supabase Auth account | mitigate | The flow NEVER calls auth.updateUser/verifyOtp and never writes auth.users — asserted by the acceptance grep (no updateUser / auth.users in confirm).
