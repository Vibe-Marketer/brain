# Phase 08.1: Connector Transcript Normalization - Patterns

**Date:** 2026-06-10

## Source of Truth Pattern

- Canonical DB row: `recordings`
- Structured transcript storage: `recordings.transcript_segments`
- Compatibility/search transcript: `recordings.full_transcript`
- Speaker/participant identity table: `call_participants`

Use `recordings.transcript_segments` before reparsing `full_transcript`.

## Provider Notes

- Read.ai: speaker object can include name/email; offsets are ms.
- Grain: transcript segment has `participant_id`; join against `participants` to recover email when possible; offsets are ms.
- Fireflies: sentences include speaker fields and second offsets; duration is minutes in `Transcript.duration` but sanity-checked against sentence offsets.
- PLAUD: mixed API shapes; segments often include speaker name and millis offsets, rarely email.
- Zoom: VTT gives speaker labels and timestamps; emails usually absent.
- Fathom: legacy `fathom_transcripts` rows already preserve speaker/email/timestamps for legacy imports.
- YouTube: segments are speakerless; do not invent a speaker.
- Paste/manual: existing parser segments already provide a segment object.
- MCP manual import: current text-only ingest needs optional structured speaker/segment support or a deterministic parser fallback.

## Landmines

- Do not make `call_participants` identity dedupe name-only; email must win when available.
- Do not overwrite user-edited transcript text/speaker fields during backfill.
- Do not remove `full_transcript`, because global search and AI tools still rely on it.
- Do not make provider-specific UI branches beyond the intentional speakerless YouTube view.
- Do not split MCP response shape into JSON; keep `content[].text` markdown.
