# Phase 08.1: Connector Transcript Normalization - Research

**Status:** Complete
**Date:** 2026-06-10

## Research Complete

Phase 08.1 should fix a real data-loss boundary, not just a rendering bug. Several connector adapters already normalize provider transcript turns in memory, but `canonicalToConnectorRecord()` drops those turns before `runPipeline()` inserts the recording. Downstream surfaces then reparses `recordings.full_transcript`, which loses speaker email, precise offsets, participant identity, and provider-specific duration semantics.

## Current Shape

### Canonical Connector Boundary

- `supabase/functions/_shared/canonical-recording.ts`
  - Defines `CanonicalTranscriptTurn` with `speakerName`, `speakerEmail`, `text`, `startSeconds`, and `endSeconds`.
  - Defines `CanonicalRecording`, but it does not currently carry `transcriptTurns`.
  - `formatCanonicalTranscript(turns)` flattens turns to `[M:SS] Speaker: text`.
  - `canonicalToConnectorRecord()` returns `ConnectorRecordLike` without `transcript_segments`.
- `supabase/functions/_shared/recording-connectors.ts`
  - `runCanonicalConnectorPipeline()` only calls `canonicalToConnectorRecord(recording, options)` and then `runPipeline()`.
- `supabase/functions/_shared/connector-pipeline.ts`
  - `ConnectorRecord` has no `transcript_segments`.
  - `insertRecording()` inserts `full_transcript`, `duration`, and metadata, but not `recordings.transcript_segments`.
  - `insertTranscriptSpeakerParticipants()` only reads `source_metadata.transcript_speaker_names`, dedupes by lowercase name, and inserts `call_participants` rows with `email: null`.

### Existing Structured Storage

- `recordings.transcript_segments` already exists in generated types and the paste path.
- `supabase/functions/save-pasted-transcript/index.ts`
  - Stores structured parsed segments for VTT, SRT, Loom, and Fathom-style paste flows.
  - Uses `runPipeline()` for new manual inserts, then updates `recordings.transcript_segments`.
  - This proves the storage column is already production-shaped enough for Phase 08.1.

### Provider Adapter State

- Read.ai: `readAiTranscriptToTurns()` preserves speaker object name/email and ms offsets, but the resulting turns are flattened before insert.
- Grain: `grainTranscriptToTurns()` preserves speaker name and ms offsets; participant emails live in `participants`, but transcript turn emails are not resolved from `participant_id`.
- Fireflies: `firefliesSentencesToTurns()` preserves speaker name and start/end seconds; host/attendees are present, but speaker email mapping is not carried per turn.
- PLAUD: `plaudTranscriptTurns()` preserves speaker name and millis offsets when available, no reliable email.
- Zoom: `zoom-sync-meetings` and `zoom-webhook` parse VTT segments, insert legacy `fathom_transcripts` rows for compatibility, and separately insert speaker-only `call_participants`; they do not store `recordings.transcript_segments`.
- Fathom: legacy sync paths write `fathom_transcripts` rows and `full_transcript`; canonical recording rows still rely on parsing or legacy table fallback.
- YouTube: `youtube-import` can parse segment arrays with `start` and `duration`, but stores speakerless `[M:SS]` text in `full_transcript`.
- MCP manual import: `ingest_transcript` writes only `full_transcript` today; speaker parameters are applied after insert, not as transcript segments.

### Display and Export Consumers

- `src/hooks/useCallDetailQueries.ts`
  - Parses `full_transcript` with a regex as the primary method.
  - Falls back to `fathom_transcripts` only for numeric legacy IDs.
  - Has no read path for `recordings.transcript_segments`.
- `src/components/call-detail/CallTranscriptTab.tsx`
  - Chat bubbles and blue host alignment depend on parsed display segments and speaker email/name heuristics.
- `src/lib/export-utils.ts` and `src/lib/export-utils-advanced.ts`
  - TXT/PDF/DOCX/Markdown/Obsidian/AI exports use `full_transcript` directly or reparse it.
- `supabase/functions/callvault-api/routes/calls.ts`
  - REST call detail returns `transcript: full_transcript`, not structured segments.
- `supabase/functions/mcp-server/tools/read/get_transcript.ts`
  - MCP transcript read returns `full_transcript` markdown.
- `src/services/api-tokens.service.ts`
  - Obsidian ZIP export selects `full_transcript` and `source_metadata`, not `transcript_segments`.

## Recommended Architecture

Use `recordings.transcript_segments` as the canonical structured transcript store for v1. It already exists, avoids a schema-expansion phase, and supports manual paste. Keep `full_transcript` as the searchable/export fallback for global search and compatibility.

Canonical segment JSON should use one stable shape:

```ts
{
  id: string;
  speaker_name: string;
  speaker_email: string | null;
  text: string;
  timestamp: string;
  start_seconds: number | null;
  end_seconds: number | null;
  provider_speaker_id?: string | null;
}
```

The canonical edge contract should add `transcriptTurns?: CanonicalTranscriptTurn[]` to `CanonicalRecording` and `transcript_segments?: CanonicalTranscriptSegment[] | null` to `ConnectorRecord`. `canonicalToConnectorRecord()` should transform turns into `transcript_segments`, preserve them in `recordings.transcript_segments`, and still generate `full_transcript` via `formatCanonicalTranscript()`.

Participant population should move from name-only insertion to an upsert helper that accepts structured identities from transcript turns, provider participants, and recorded-by metadata. Deduping should prefer normalized email, then normalized name; it must avoid inserting duplicate `Unknown` participants and must not overwrite existing CallVault-owned edits.

## Validation Architecture

1. Unit tests for canonical helpers:
   - `CanonicalRecording.transcriptTurns` becomes `ConnectorRecord.transcript_segments`.
   - offsets format to timestamps.
   - speaker emails survive.
   - `full_transcript` remains populated as fallback.
2. Provider fixture tests:
   - Read.ai, Grain, Fireflies, PLAUD, Zoom, Fathom, YouTube, paste/manual, and MCP manual import each produce expected canonical segments, duration seconds, and participants.
3. UI tests:
   - `useCallDetailQueries` prefers `recordings.transcript_segments` over regex parsing.
   - speaker grouping and host alignment use structured email/name data.
   - speakerless YouTube remains paragraph style without fake speaker attribution.
4. API/export tests:
   - REST and MCP expose stable transcript text derived from structured segments when present.
   - Obsidian and smart export include participants/speaker order from canonical data.
5. Backfill/lazy normalization test:
   - existing flattened recordings can be normalized once without duplicate recordings, duplicate workspace entries, or overwritten user edits.

## Risks and Constraints

- Do not make UI components own provider-specific normalization. Provider quirks belong in adapters or shared helpers.
- Do not remove or stop writing `full_transcript`; search, AI tools, and compatibility still depend on it.
- Do not use `parseInt()` or `Number()` on mixed recording IDs in frontend changes. Use canonical UUID paths for `recordings.transcript_segments`.
- Do not broaden MCP response shape beyond `content[].text` markdown.
- Do not add file-upload or async transcription scope.
- Integration tests that touch Supabase must use real test DB guards, not mocked Supabase.
