# Plan 36-02: BUG-03 — Cache Invalidation on Mutations

## Goal

After a user moves, deletes, or tags a call, the call list MUST refresh immediately without manual page reload. Toast success and visible table state must agree.

## Root Cause Hypothesis (audit-driven)

TanStack Query mutations across `useFolderAssignment`, `useFolders` (move/remove), `useCallDetailMutations` (delete), `useTags` (assign/unassign), and `useWorkspaceAssignment` either:
- Invalidate a stale or differently-shaped query key than the parent list (e.g., `['workspace-entries']` vs `queryKeys.workspaceEntries.all`)
- Do not invalidate the canonical call-list query at all (`queryKeys.calls.all` or the workspace-entries hub query)
- Invalidate only on `onSuccess` but the parent list is held in a Zustand store + TanStack cache combo, missing the second hub

This plan audits every call-list mutation, normalizes the query-key invalidation pattern, and adds a real-DB regression test that proves the visible cache flips immediately after mutation.

  queryClient.invalidateQueries({ queryKey: queryKeys.calls.all })

}
