# Phase 38 — UI Design Contract

> Visual and interaction contract for recording access policy, private copy discovery, and access requests. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Source and Decision Precedence

This contract applies the locked decisions in `38-CONTEXT.md`. If an older source document describes separate owner-editable content and existence controls, the current contract wins: the owner chooses one recording access level, while privacy-safe existence discovery remains a system rule limited to verified participants and eligible event sizes/types.

The UI must never imply that access to one recording controls another attendee's copy. Existing team access, coach access, and share links continue to work and remain managed through their existing surfaces.

---

## Visual Hierarchy

1. **Current access level** is the primary information in both Settings and the recording panel.
2. **Inherited versus custom state** is visible beside the current level, never hidden in helper text.
3. **Pending requests** appear before active grants when at least one request exists, so owners can act without scanning the whole panel.
4. **Active grants** are secondary management rows with a quiet `Revoke access` action.
5. The sentence **“This controls your recording only. Other attendees control their own copies.”** is always visible in the recording access panel, including loading and error states.
6. Anonymous copy rows stay visually neutral. They must not look like normal recording cards because a normal card's title, owner, source, thumbnail, or metadata would disclose protected information.

Vibe orange remains a structural accent for selected navigation, focus, unread state, and links. It is not used as a privacy level color or to make Public look promotional.

## Surface 1 — Settings > Privacy & Access

### Navigation and page contract

- Add a settings category with label **“Privacy & Access”** and description **“Defaults for new recordings”**.
- Place it immediately after **Account** in `SettingsCategoryPane`; it is available to every authenticated user and has no ADMIN or TEAM role requirement.
- Use the existing `SelectionButton` navigation treatment and `PageHeader` layout. The route follows the current settings URL pattern: `/settings/privacy-access`.
- Page title: **“Privacy & Access”**.
- Page subtitle: **“Choose how new recordings start.”**

### Default access control

- Section heading: **“Default access for new recordings”**.
- Supporting copy: **“New recordings use this access level. Changing it won't update recordings you already have.”**
- Render the six choices as one labeled `RadioGroup`, not six unrelated buttons and not a toggle:

| Value | Label | Description |
|-------|-------|-------------|
| `private` | Private | Only you and people you explicitly grant access to. |
| `attendees` | Attendees | Confirmed meeting attendees can view the recording. |
| `invitees` | Invitees | People invited to the meeting can view the recording. |
| `organization` | Organization | People in your organization can view the recording. |
| `link` | Anyone with link | People with an active CallVault share link can view the recording. |
| `public` | Public | Anyone can view the recording without an invitation or share link. |

- The initial default is **Private**.
- Save immediately after a non-Public selection. Do not add a page-level Save button.
- During save, disable only the group, retain its layout, and show an inline spinner beside the selected value. Update optimistically; restore the previous selection if the server rejects the change.
- Success toast: **“Default access set to [level].”**
- Failure toast: **“Couldn't update the default. Your previous setting is still active. Try again.”**
- The account default is copied onto each new recording. It is not a live link. Changing the setting never changes existing recordings.

### Public default confirmation

Selecting Public opens an `AlertDialog` before the value changes:

- Title: **“Make new recordings public by default?”**
- Description: **“Every new recording will be publicly viewable unless you change its access level. Existing recordings will not change.”**
- Cancel: **“Keep current default”**
- Confirm: **“Use Public by default”**

Cancel restores focus to the Public radio option without selecting it. Confirm performs the normal save behavior.

## Surface 2 — Recording Access Button and Compact Panel

### Entry point and permissions

- Add a hollow **“ACCESS”** button with a Remix lock/shield icon immediately before the existing **“SHARE”** button in `CallDetailHeader`.
- Only the recording owner sees this management button. Other viewers do not receive a disabled button or tooltip that hints at owner controls.
- Keep the existing Share dialog unchanged. Access policy management must not absorb share-link creation or revocation.
- Desktop and tablet: open an anchored Radix `Popover`, aligned to the Access button, `w-[400px] max-w-[calc(100vw-16px)]`, with a `ScrollArea` capped at `70vh`.
- Mobile: present the same content in a Radix `Dialog` sized to the viewport gutters. Use `useBreakpointFlags()` rather than CSS-only duplicate interactive trees.
- Panel heading: **“Recording access”**.

### Persistent copy-only notice

Directly below the panel heading, always render this sentence in a neutral `bg-muted/60` callout:

> **This controls your recording only. Other attendees control their own copies.**

Below it, use smaller helper copy:

> Existing team, coach, and share-link access remains active.

The notice remains rendered while policy, grants, or requests are loading or in an error state.

### Policy state

- Render one **“Access level”** section using the shared six-option `AccessLevelPicker` and exact option copy from Settings.
- Show one state badge next to the section heading:
  - **“Using default: [level]”** when the recording was created or last reset from the account default.
  - **“Custom”** when the owner explicitly chose a per-recording override.
- “Using default” records how the stored value was set. It does not mean the recording follows future account-default changes.
- When state is Custom, show a link-style action **“Reset to default”**. Activating it copies the account's current default onto this recording and returns the badge to **“Using default: [level]”**.
- Any explicit level selection in this panel produces Custom state, even if the selected value currently matches the account default. The Reset action is the sole explicit route back to inherited state.
- Apply ordinary non-Public changes immediately, with optimistic state and rollback on failure.
- Success toast: **“Recording access updated.”**
- Reset success toast: **“Recording access reset to [level].”**
- Failure toast: **“Couldn't update recording access. Nothing changed. Try again.”**

### Public recording confirmation

Selecting Public opens an `AlertDialog` before the policy changes:

- Title: **“Make this recording public?”**
- Description: **“Anyone can view “[recording title]” without a direct invitation or share link. This affects this recording only.”**
- Cancel: **“Keep current access”**
- Confirm: **“Make public”**

Do not use a red destructive button for making a recording Public. Use the normal primary button and the explicit confirmation copy.

### Pending requests

- Section label: **“Access requests ([count])”** using `tabular-nums` for the count.
- When count is greater than zero, place this section before People with access.
- Each compact row shows requester's name, verified email, relative request time, and a hollow **“Review request”** button.
- It never shows a requester-authored message because the request flow has no message field.
- Empty heading: **“No pending requests”**
- Empty body: **“New requests will appear here.”**

### Active request-based grants

- Section label: **“People with access ([count])”** using `tabular-nums`.
- Each row shows name, verified email, **“Granted [date]”**, and a link-style **“Revoke access”** action.
- This list contains request-based individual grants only. It does not duplicate team, coach, organization, Public, or share-link access.
- Empty heading: **“No individual access grants”**
- Empty body: **“Approved requests will appear here. Share links stay under Share.”**

Revocation requires an `AlertDialog`:

- Title: **“Revoke access for [name]?”**
- Description: **“[Name] will lose access to this recording. This action is logged.”**
- Cancel: **“Keep access”**
- Confirm, destructive variant: **“Revoke access”**

On success, remove the grant and announce **“Access revoked for [name].”** in a toast and polite live region. On failure, restore the row and show **“Couldn't revoke access. Nothing changed. Try again.”**

## Surface 3 — Anonymous Other-Copy Discovery

### Attachment point

- Add a section at the end of the existing Call Overview scroll content, after normal details and source content.
- Section heading: **“Other recordings from this meeting”**.
- Render the section only after the server confirms all three conditions: the viewer is a confirmed participant with verified evidence, at least one inaccessible copy exists, and the event is neither provider-identified as a webinar nor at or above 50 confirmed participants.
- If any condition fails, render nothing: no heading, count, empty state, disabled button, or explanation.

### Anonymous row contract

- Render one neutral bordered row per inaccessible copy, numbered sequentially **“Recording 1”**, **“Recording 2”**, and so on.
- Supporting text: **“Another recording from this meeting.”**
- Active CTA: **“Request access”**.
- The row and its accessible name must not contain the recording owner, provider, real recording title, summary, transcript excerpt, thumbnail, URL, source icon, duration, creation time, organization, or workspace.
- Numbers are presentation labels scoped to the current response; they are not stable identifiers and must not be placed into a URL or analytics event as if they were record IDs.
- The underlying recording identifier must never be exposed in visible copy, DOM test IDs, client logs, or an unauthenticated URL.

### Request interaction and requester states

- Requesting is one click. Do not open a form, textarea, or confirmation dialog.
- While submitting, disable only that row's action and label it **“Sending…”**.
- Success state: disabled **“Request sent”** with a Remix check icon.
- Success toast: **“Access request sent. The recording owner has been notified.”**
- Submission failure: restore **“Request access”** and show **“Couldn't send your request. Try again.”**
- During a denial cooldown, show disabled **“Available [date]”**; include the full explanation in an accessible description: **“You can request access again on [full date].”**
- After approval, invalidate the event-copy and call-list queries. Replace the anonymous row with the app's normal accessible recording treatment only after the grant is confirmed by the server.
- If a grant is later revoked, the copy returns to its anonymous request state only when the same verified-participant and event-cap checks still pass.

No client-side filtering is an acceptable privacy gate. The response itself must omit protected fields and return no rows for unqualified viewers or capped event types/sizes.

## Surface 4 — Owner Review, Notifications, and Email Entry

### In-app owner notification

Extend the existing `NotificationBell` row pattern rather than creating a second notification center.

- Title: **“Access requested”**
- Body: **“[Name] requested access to “[meeting title]”.”**
- Row action: **“Review request →”**
- Unread treatment, orange dot, relative time, dismiss behavior, and keyboard behavior match current notification rows.
- Activating the notification marks it read, opens the target call, opens Recording access, and focuses the referenced pending request.

### Email entry

- Subject: **“Access requested for “[meeting title]””**
- Primary email CTA: **“Review request”**
- The direct link opens the same authenticated review state. If signed out, authentication returns the owner to that review state.
- Email body includes requester's name and verified email, meeting title/date, and a concise statement of verified participation evidence. It contains no requester message field.

### Review state

The focused review card/panel shows these labeled values in order:

1. **Requester** — name
2. **Verified email** — verified address
3. **Meeting** — title
4. **Meeting date** — localized date and time
5. **Verified participant evidence** — concise evidence returned by the server

Actions:

- Primary: **“Approve access”**
- Secondary destructive text/button: **“Deny request”**

Approval is one click and does not open another confirmation. On success, move the person from pending requests to People with access and show **“Access approved for [name].”** Approval remains active until revoked.

Denial opens an `AlertDialog`:

- Title: **“Deny this access request?”**
- Description: **“[Name] won't get access and cannot request this recording again for 30 days. No private reason will be shared.”**
- Cancel: **“Keep request”**
- Confirm, destructive variant: **“Deny request”**

On success, remove the pending row and show **“Access request denied.”** On failure, restore the row and show **“Couldn't update this request. Nothing changed. Try again.”**

If a notification or email link targets a request that was already resolved, show the non-error status **“This request has already been [approved/denied].”** If the request is unavailable or the viewer is not its owner, show **“This access request is no longer available.”** Do not disclose the current owner or recording state.

### Requester result notifications

- Approved title: **“Access approved”**
- Approved body: **“You can now view “[meeting title]”.”**
- Approved action: **“Open recording →”**
- Denied title: **“Access request denied”**
- Denied body: **“Your request for “[meeting title]” wasn't approved. You can request again after [date].”**
- A denial never includes a private reason.

## Loading, Empty, Error, and Concurrency States

| Surface | Contract |
|---------|----------|
| Settings initial load | Use `Skeleton` rows matching the radio-choice height; do not briefly show Private before the stored preference resolves. |
| Access panel initial load | Keep heading and required notice visible; skeleton the state badge, choice rows, requests, and grants. |
| Access panel fetch error | Show the exact panel load error and a hollow **“Retry”** action. Do not show editable controls based on stale or guessed policy. |
| No requests/grants | Render the exact empty copy above; do not remove the section headings. |
| Anonymous discovery query | Render no discovery section until the server returns an authorized, non-capped result. After eligibility is established, a retryable inline error may use the exact discovery error copy. |
| Duplicate request | Resolve to the existing state (`Request sent` or cooldown date); do not create a second row or show a generic failure. |
| Concurrent owner action | Disable the affected request/grant row only. Server state wins; on conflict, refetch and show **“This request changed. The latest status is shown.”** |
| Deep-linked resolved request | Show the already-approved/already-denied status and current panel lists; never re-enable the original action. |
| Offline/network loss | Roll back optimistic state, retain the open surface, and use the declared failure copy. |

## Responsive Behavior

| Breakpoint | Contract |
|------------|----------|
| Desktop (`>=1024px`) | Existing four-pane shell remains unchanged. Access opens as a 400px anchored popover. Anonymous rows keep label and CTA on one line. |
| Tablet (`768–1023px`) | Sidebar follows existing auto-collapse. Access remains an anchored popover but clamps to viewport gutters. |
| Mobile (`<768px`) | Settings uses the existing single-pane navigation/back behavior. Access content uses a Radix Dialog with `max-h-[calc(100vh-16px)]`. Long names and emails truncate visually with a native/title or accessible full-value affordance. Meeting titles wrap to two lines in review state. Evidence text wraps naturally and never forces horizontal scrolling.

## Accessibility Contract

- The access-level group has a visible label and one keyboard-navigable `RadioGroup`; arrow keys move choices according to Radix behavior.
- Every icon is decorative (`aria-hidden="true"`) unless it is the only content of a control. Icon-only controls require an explicit `aria-label`.
- Anonymous request buttons use labels such as **“Request access to recording 1”** while keeping the visible text **“Request access”**.
- Status badge text is real text, not color-only. Public, Custom, inherited, pending, granted, denied, and cooldown states remain distinguishable without color.
- Mutation results are announced through `aria-live="polite"`; failures use `role="alert"` where immediate correction is needed.
- `AlertDialog` owns focus while open, Escape cancels, and focus returns to the initiating control after close.
- Opening a notification deep link moves focus to the review heading after the call and access panel finish loading.
- Dismiss notification remains a separate button and never nests inside the notification action button.
- All interactive controls retain the existing vibe-orange focus ring and meet mobile touch-target requirements.
- Reduced-motion preference disables nonessential panel and row motion while preserving state changes.

## Motion

- Reuse existing Radix popover/dialog transitions and the app's established motion timing. Do not add a new animation library.
- Request rows may cross-fade when moving between pending and granted lists, using `motion/react` only if motion materially clarifies the state change.
- No celebratory animation follows Public, approval, denial, or revocation.
