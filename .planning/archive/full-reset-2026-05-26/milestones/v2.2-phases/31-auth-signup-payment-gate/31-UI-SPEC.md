Exceptions: **none**. All values are multiples of 4 and match the existing Tailwind defaults.

### Accent (`vibe-orange`) reserved for — explicit list

In this phase, the vibe-orange accent is reserved for **exactly two surfaces** (and nowhere else):

1. The "Sign up → view plans" CTA — specifically the **arrow glyph** (`RiArrowRightLine`) at the end of the link in the mode-switcher row, rendered as `text-vibe-orange`. The text itself stays `text-foreground` — only the arrow uses the accent to draw the eye to the conversion path.
2. The "$ Upgrade required" callout on the payment-gate intermediate screen (if user lands there before the redirect fires) — a single `text-vibe-orange` lockup icon (`RiLockLine`) at the top of the redirect message.

Forbidden uses of vibe-orange in this phase:
- ❌ Primary "Sign in" / "Create account" submit buttons (those use `bg-foreground text-background` — the existing slate gradient pattern)
- ❌ Form input focus rings (use the default shadcn focus ring)
- ❌ "Continue with Google" button (uses `variant="hollow"` — bordered, no accent)
- ❌ "Send me a magic link" button (also `variant="hollow"`)
- ❌ Hyperlinks ("Forgot password?", "Sign in instead") — those stay `text-foreground hover:underline`
- ❌ Toast backgrounds — Sonner uses its own semantic colors

### Destructive

No destructive buttons in this phase. The "delete soren canary account" task is operator-side (Supabase admin SQL/API per CONTEXT.md `### Soren Canary Account — Delete`), not a UI surface.

### Toast / inline error copy

All errors flow through `getErrorToastMessage(error)` from `src/lib/user-friendly-errors.ts`. Phase 31 extends that function to handle **Supabase Auth-specific** messages. Each row below is a NEW mapping the executor must add:

| Supabase error substring (case-insensitive match) | Toast copy | Toast type | Action hint suffix |
|----|----|----|----|
| `user already registered` | `This email is already registered. Sign in instead.` | `toast.error` | none — drop the `(Try Again)` suffix; this is an actionable redirect, not a retry |
| `password should be at least 6 characters` | `Password must be at least 6 characters.` | `toast.error` | none |
| `weak password` (covers Supabase's strength checker) | `Try a stronger password — mix letters, numbers, and a symbol.` | `toast.error` | none |
| `email rate limit exceeded` | `Too many signup attempts. Try again in a few minutes.` | `toast.error` | none |
| `over email send rate limit` | `Too many emails sent. Wait a few minutes and try again.` | `toast.error` | none |
| `email not confirmed` | `Check your email and click the confirmation link to continue.` | `toast.error` | none |
| `invalid login credentials` (the wrong-password / wrong-email case — QA-20) | `Invalid email or password. Check your spelling or reset your password.` | `toast.error` | none |
| `signup is disabled` | `New signups are temporarily paused. Try again later.` | `toast.error` | none |
| `email address is invalid` (server-side, in case Zod missed it) | `That email address doesn't look right. Check the spelling.` | `toast.error` | none |
| (Anything else) | Fall through to existing `getUserFriendlyError` generic copy chain. **Never** emit the bare string `An unexpected error occurred` — the existing fallback already says `An unexpected error occurred. Try again - if it keeps happening, contact support.` which is acceptable; if the executor encounters a path that produces the bare string, that's a bug to fix. | — | — |

### OAuth wrong-recipient (Google sign-in → shared call) — AUTH-05

When a Google-authenticated user lands on a shared-call URL where they aren't the authorized recipient:

- **Until Phase 32 ships the backend signal:** the share-call page can only show generic "Call Not Found". The Phase 31 surface-level change is to ensure the `pendingShareToken` is threaded through OAuth so the user lands on `/s/{token}` (not the home page), where the existing share-call view fires.
- **Inline error copy on the share-call view when the backend returns a distinguishable wrong-recipient response (Phase 32 enables this):** Heading: `This share is for a different account` — Body paragraph: `This call was shared with {recipientEmail}. Sign out and sign back in with that account, or ask the sender to re-share it.` — Primary button: `Sign out`. (This row is the **forward-compatible contract** — Phase 31 plumbs the token; the actual error UI activates when Phase 32 backend lands. The string is locked here so we don't re-design it in Phase 32.)

### Empty states

This phase has no list views or empty data states. The closest analog — "no plan selected" — is handled by the **payment gate redirect screen** (covered above under "Headings" and "Primary CTAs"), which is not an empty state per se but a transitional state with a clear action.

### Destructive actions / confirmation approach

No destructive UI surfaces in this phase. The single destructive operation — deleting `soren@vibeos.com` from Supabase Auth — is performed by the operator via Supabase admin SQL or the admin dashboard (CONTEXT.md `### Soren Canary Account — Delete`). It does not appear in any user-facing or admin-facing CallVault UI.

If, during plan-phase, an admin "Delete user" UI is added (unlikely scope creep), the confirmation approach must be: Radix `<Dialog>` with double-confirm (type the email to confirm), destructive button uses `variant="destructive"`, title: `Delete account permanently?`, body: `This will delete {email}'s account and all associated data. This cannot be undone.`, primary button: `Delete account`, secondary button: `Cancel`. **Not in scope for Phase 31** — call out only.

## Interaction Patterns

| Pattern | Spec |
|---------|------|
| Sign-up CTA click | Immediately `window.location.href = 'https://callvaultai.com/pricing?ref=app'` — preserve any existing `?next=` param via a sessionStorage write before the redirect (`pendingNext` key). No intermediate screen. No loading spinner — the browser navigation handles the transition. |
| Form-submit during loading | Button disabled, label changes to `-ing...` variant (`Signing in...` / `Creating account...`). Inputs disabled. No spinner inside the button — text-only state change matches existing pattern. |
| Successful signup (with email confirm pending) | Full-screen state swap inside the card: form unmounts, "Check your email" content mounts. Mirror `ForgotPassword.tsx:65-86` structure exactly — bordered callout + hollow "Back to sign in" button. |
| Successful signup (immediate session) | Toast (`Account created — welcome to CallVault!`) + `navigate(getPostLoginRedirect())`. No screen swap. |
| Failed signup / signin | Toast.error with mapped copy (see Toast copy table). Inputs stay populated. Loading state clears. No card-level error banner — toasts handle it. |
| OAuth callback with pending share token | `OAuthCallback.tsx` reads `sessionStorage.pendingShareToken`; if present, redirect target becomes `/s/{token}` instead of `/`. Existing full-screen spinner stays. No new UI. |
| Payment gate redirect | On `/onboarding` mount, `useRequirePaidPlan()` runs. If user lacks paid plan AND is not grandfathered → render the **payment gate redirect screen** for 800ms (so users see what's happening), then `window.location.href = 'https://callvaultai.com/pricing?reason=gate&user={user_id}'`. If the redirect is blocked (rare), the manual "Continue to pricing" button stays clickable. |
| Toast positioning | Inherits the global Sonner config — top-right on desktop, top-center on mobile. No per-toast position overrides in this phase. |
| Toaster mount verification | The Sonner `<Toaster />` MUST be mounted at the `App.tsx` root level (above the router), NOT inside any individual route. The plan-phase must explicitly verify this — if Toaster is route-scoped today, that's the AUTH-01 silent-failure root cause to fix. |

## Accessibility Contract

| Item | Requirement |
|------|-------------|
| Form labels | Every `<Input>` has an associated `<Label>` with `htmlFor`. Already in place — keep. |
| Focus order | Email → Password → primary submit → "Continue with Google" → "Send me a magic link" → "Forgot password?" → mode-switcher. Default DOM order achieves this; do not introduce `tabIndex` overrides. |
| Icon-only buttons | None. All buttons in this phase have visible text labels. |
| Decorative icons inside inputs | `RiMailLine` and `RiLockLine` rendered as visual decoration inside the input — add `aria-hidden="true"` if not already present. |
| Color contrast | All text uses semantic tokens (`text-foreground`, `text-muted-foreground`) which meet WCAG AA at the configured token values. No hardcoded colors that could fail contrast. |
| Loading announcements | Button label text changes (e.g. `Sign in` → `Signing in...`) which screen readers announce. No `aria-live` needed beyond this. |
| Toast accessibility | Sonner's built-in `role="status"` is sufficient. No overrides needed. |
| Confirmation screen | The "Check your email" screen replaces the form on the same route — no focus management needed beyond default (browser will keep focus on the now-unmounted submit button → focus falls to body, which is acceptable). If smoother UX is wanted, plan-phase can add a `useEffect` to focus the "Back to sign in" button on mount. |
