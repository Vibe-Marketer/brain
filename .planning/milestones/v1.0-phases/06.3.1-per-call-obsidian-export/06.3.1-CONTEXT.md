# Phase 06.3.1: Per-call Obsidian export - Context

**Gathered:** 2026-06-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 06.3.1 adds a per-call Obsidian export action from an individual call/transcript surface. It should let a user export the currently viewed call as Obsidian-compatible markdown without using the full-vault ZIP flow.

This phase does not add an Obsidian plugin, does not restore an `obsidian-sync` backend, does not change API-token semantics, does not alter the full-vault Obsidian ZIP behavior except for shared utility extraction if useful, and does not touch the `legacy_recording_id` to `fathom_provider_id` rename owned by Phase 06.3.2.

</domain>

<decisions>
## Implementation Decisions

### Export Surface and User Flow

- **D-01:** The per-call Obsidian action should live in the existing call/transcript action menu or export menu as `Export to Obsidian`, not as a new large primary button or hero surface.
- **D-02:** The per-call path should be action-first and one-click where possible: the user opens the call, chooses the Obsidian export action, and gets the note without extra setup.
- **D-03:** The action should be available from the individual call/transcript context, not from Settings. Settings remains the full-vault export and API-token/plugin setup surface from Phase 06.3.

### Output Shape

- **D-04:** The primary output is a single `.md` file for the current call, not a ZIP and not a `CallVault/{org}/{workspace}/` folder tree. Per-call export should produce an inspectable standalone note.
- **D-05:** The note must use the same Obsidian-compatible markdown conventions as the full-vault export: YAML front matter, readable call note body, `# {title}`, date, duration when known, workspace when known, participants as Obsidian wikilinks when known, optional summary, and a `## Transcript` section.
- **D-06:** The per-call filename should follow the existing Obsidian filename convention from `exportToObsidian()`: `{date}-{slug}.md`, with filesystem-safe slugging and deterministic fallback for missing title/date. It does not need duplicate-path suffixing unless the implementation reuses a generic helper that already supports it.
- **D-07:** `vault_path` in front matter should remain meaningful for Obsidian users. For a standalone per-call file, it may represent the recommended destination path (`CallVault/{org}/{workspace}/{date}-{slug}.md`) even though the browser downloads only the `.md` file.

### Copy Markdown

- **D-08:** Add `Copy Obsidian markdown` alongside the file download if it is cheap and fits existing menu patterns. It should copy the exact same markdown content that download writes.
- **D-09:** If planner research finds copy support materially increases scope or conflicts with existing UI affordances, download-only is acceptable for this phase. Do not block the core per-call download on copy support.

### Metadata and Data Semantics

- **D-10:** Carry forward Phase 06.3 metadata expectations for per-call notes: title, date/date_time, duration, organization/workspace when available, participants, tags if available, transcript presence, canonical CallVault UUID, share/source URL where available, and synced/exported timestamp.
- **D-11:** Prefer canonical UUID identity in front matter (`recordings.id` / `canonical_uuid`). Do not introduce new dependencies on numeric Fathom IDs.
- **D-12:** Preserve stored transcript text. If stored transcript lines already include speaker attribution or timestamps, preserve them; do not synthesize false speaker/timestamp precision.
- **D-13:** Missing transcript should render an explicit `Transcript not available.` message instead of producing a blank or failed note.
- **D-14:** Use existing share/source URL helper patterns where applicable; do not hand-roll Fathom-only URL extraction if a canonical helper is available.

### Architecture and Reuse

- **D-15:** Reuse or extract the markdown-note construction logic from `src/lib/export-utils.ts` so full-vault and per-call Obsidian exports do not drift in front matter/body format.
- **D-16:** The existing `exportToObsidian()` may continue creating ZIPs for multi-call/full-vault flows. If needed, extract a pure helper such as `buildObsidianMarkdown()` / `buildObsidianFileName()` and have both flows call it.
- **D-17:** Preserve service + hook/component separation. Components should not fetch extra DB data directly; they should use existing call detail data or established services/hooks.
- **D-18:** Keep UI copy in the "AI-ready, not AI-powered" brand lane. This feature is about portability and Obsidian-ready notes, not "AI-powered" export.

### Verification

- **D-19:** Add focused tests for the extracted per-call markdown builder or export helper: front matter fields, filename slugging, missing transcript handling, participant wikilinks, summary inclusion, transcript preservation, and share/source URL preservation.
- **D-20:** Add UI-level or hook-level verification that the menu action triggers a `.md` download for a call and that copy markdown writes the same content if copy is included.
- **D-21:** Run `npm run type-check` and `npm run build` before claiming the phase planned/executed successfully. If UI changes are implemented, browser/screenshot verification should prove the menu action is reachable and not visually disruptive.

### the agent's Discretion

The user approved the recommended defaults. Downstream agents may choose the exact component/menu placement, helper names, test file boundaries, and whether copy support fits the phase, provided the decisions above are preserved and the implementation stays tightly scoped to per-call Obsidian export.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `exportToObsidian(calls, orgName, excludedWorkspaceNames)` in `src/lib/export-utils.ts` currently builds Obsidian-compatible markdown files and saves them inside `callvault-obsidian-{date}.zip`.
- `buildObsidianFrontmatter()` and filename/path helpers in `src/lib/export-utils.ts` contain the front matter, `vault_path`, participant wikilink, tag, transcript presence, and path-sanitizing conventions this phase should reuse or extract.
- `useTranscriptExport()` in `src/hooks/useTranscriptExport.ts` already handles single-call copy/export interactions and `file-saver` downloads; it is a likely analog for the UI/hook side.
- `SmartExportDialog` already routes selected calls through export utilities, including Obsidian Vault mode, and can guide how existing export menus are composed.

### Established Patterns

- Full-vault export creates a ZIP; per-call export should create a single `.md` file.
- Existing export utilities use `file-saver` for downloads and lazy-import heavy libraries such as `jszip`, `jspdf`, and `docx`.
- Existing Obsidian markdown body includes YAML front matter, title, date, duration, workspace, participants, optional summary, and transcript or `Transcript not available.`.
- UI should use Remix icons if adding menu/action icons; Lucide and FontAwesome are banned.

### Integration Points

- Individual call/transcript action menu or export menu: primary target for the new per-call action.
- Export utility layer: shared markdown builder should serve both full-vault ZIP and single-file per-call export.
- Documentation: export help should mention per-call Obsidian `.md` download if the UI exposes it.

</code_context>

<specifics>
## Specific Ideas

- User approved the recommended defaults: menu action placement, single `.md` download, optional copy markdown if cheap, no ZIP/folder tree for per-call, and Phase 06.3 metadata carried forward.
- Suggested labels: `Export to Obsidian`, `Download Obsidian note`, and, if included, `Copy Obsidian markdown`.
- Per-call export should feel like an immediate call-level action, not an integration setup flow.

</specifics>

<deferred>
## Deferred Ideas

- Full Obsidian plugin implementation, sync interval design, and plugin docs remain future REST/API integration work.
- Reintroducing `obsidian-sync` or a separate `token_source = 'obsidian'` remains out of scope.
- Full-vault export scale/hardening stays with Phase 06.3 context unless planning finds a small shared-helper adjustment is needed for per-call reuse.
- `legacy_recording_id` to `fathom_provider_id` rename remains Phase 06.3.2.

</deferred>
