# Phase 06.1 Plan sec-worker-bypass: Worker Bypass Security Gate Summary

x-callvault-internal-secret header validation added as first action in all three MCP Edge Functions, blocking direct Supabase URL access without the shared 32-byte secret.

## What Was Built

Added `x-callvault-internal-secret` header validation as the FIRST action in three Supabase Edge Functions that handle MCP traffic:

- `supabase/functions/mcp-server/auth.ts` — gate at top of `authenticateMcpRequest()`, before any auth token inspection
- `supabase/functions/mcp-oauth-register/index.ts` — gate after OPTIONS preflight (to preserve CORS), before POST method check
- `supabase/functions/mcp-oauth-metadata/index.ts` — gate before OPTIONS preflight (discovery docs are world-readable but must still come through the Worker)

All three functions return HTTP 403 `{"error":"forbidden"}` on absent or wrong secret. Created `cloudflare/mcp-subdomain-worker/wrangler.toml` for the new subdomain Worker (plan `worker-routing`). Set `CALLVAULT_INTERNAL_SECRET` in Supabase Edge Function secrets.

## Deviations from Plan

### Deviation 1: Cloudflare Worker secret set deferred

**Found during:** Task 1
**Issue:** `wrangler secret put CALLVAULT_INTERNAL_SECRET --config cloudflare/mcp-subdomain-worker/wrangler.toml` fails with auth error 10000 because the `callvault-mcp-subdomain` Worker script doesn't exist yet in Cloudflare — you cannot set secrets on a non-existent Worker.
**Fix:** Deferred to `worker-routing` plan which deploys the actual Worker script. The secret value (`e9e59d3d8152b123d8104ae3e2b824cd53d6afbaa1654606ea2f8953dc206cb3`) must be set in the Worker after the `worker.ts` script is first deployed.
**Impact:** Low — the Supabase-side secret is set and enforced. The Cloudflare Worker secret is needed only when the Worker itself starts injecting the header (which is the `worker-routing` plan's job).

### Deviation 2: mcp-oauth-metadata gate position

**Found during:** Task 2
**Issue:** The plan spec says "at start of Deno.serve handler, before OPTIONS handler." However the `corsHeaders` variable is initialized at the very top of the handler and needed for the 403 response. Placed the gate AFTER `corsHeaders` initialization but BEFORE the OPTIONS handler.
**Fix:** Gate is placed immediately after `const corsHeaders = getPublicCorsHeaders()` so it can include corsHeaders in the 403 response, which is the correct behavior per the plan's interface spec.
**Impact:** None — functionally identical to the spec intent.
