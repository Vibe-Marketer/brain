## Summary

Phase 6.1 is a well-scoped hardening-and-routing phase with a clear dependency graph (ISA.md provides 181 acceptance criteria). All architectural decisions are locked in CONTEXT.md. The codebase is fully legible — auth.ts, worker.ts, protocol.ts, OAuthConsentPage.tsx, McpSetupSnippets.tsx, and grant-selection.ts have been read directly. No architectural ambiguity remains; the remaining work is implementation.

The phase has four sequential layers: (1) Wave 1/1b security fixes in parallel — seven independent code/migration changes; (2) sec-slug-tombstone + slug-schema migrations (strictly sequential); (3) the new Cloudflare Worker with wildcard routing; (4) a six-way fan-out of dependent features. The only hard sequencing constraint is tombstone tables → slug columns → Worker deployment. Everything else in Wave 1 can be parallelized.

Key risks are the security gate ordering (DNS provisioning is permanently blocked until all 7 Critical/High ISCs are green), the `readClientIdFromJwt()` vulnerability that exists in production today, and the `selectOAuthGrant` silent-fallback that could grant a multi-org user's token to the wrong org. These are the three highest-priority items regardless of wave.

**Primary recommendation:** Plan Wave 1 features as fully independent plans with no task-level sequencing between them. sec-slug-tombstone must precede slug-schema in `depends_on`. The worker-routing plan must gate DNS provisioning on a `checkpoint:human-verify` that confirms all 7 security gate plans are verified-green.

### Pattern 1: Internal Secret Validation (sec-worker-bypass)

**What:** Every MCP Edge Function validates `x-callvault-internal-secret` as its first action. Returns 403 immediately if absent or wrong.
**When to use:** All MCP-related Edge Functions: mcp-server, mcp-oauth-register, mcp-oauth-metadata

```typescript
// Source: ISC-1-7 (ISA.md)
// First action in Deno.serve handler body — before CORS, before auth
const internalSecret = Deno.env.get('CALLVAULT_INTERNAL_SECRET');
const incomingSecret = req.headers.get('x-callvault-internal-secret');
if (!internalSecret || !incomingSecret || incomingSecret !== internalSecret) {
  return new Response(JSON.stringify({ error: 'forbidden' }), {
    status: 403,
    headers: { 'Content-Type': 'application/json' },
  });
}
```

Note: Must be set in both Worker env vars AND Supabase secrets. Value is 32-byte random hex. CALLVAULT_INTERNAL_SECRET should be generated via `openssl rand -hex 32`.

### Pattern 2: JWT Fix (sec-jwt-fix)

**What:** Remove `readClientIdFromJwt()` from auth.ts entirely. Extract `client_id` from the verified user object returned by `authClient.auth.getUser(rawToken)`.
**Current state:** `readClientIdFromJwt()` is at line 263 of auth.ts — base64-decodes the JWT payload without signature verification. The `client_id` claim in the JWT can be forged by any attacker who can construct a JWT with an arbitrary payload.
**Fix:** Supabase Auth's `getUser()` already returns the verified user object, which includes app_metadata. The client_id must come from `jwtUser.app_metadata?.provider` or from the verified grant lookup, not from raw token bytes.

```typescript
// Source: ISC-8-12 (ISA.md)
// REMOVE readClientIdFromJwt() entirely.
// AFTER getUser() succeeds, get client_id from user object:
const { data: { user: jwtUser }, error: jwtError } = await authClient.auth.getUser(rawToken);
if (jwtError || !jwtUser) { /* return 401 */ }

// client_id comes from app_metadata (set by Supabase Auth during OAuth flow)
const clientId = jwtUser.app_metadata?.provider_token_hash
  ?? (jwtUser.app_metadata as Record<string, unknown>)?.client_id as string | undefined
  ?? null;
// NOTE: exact field name must be verified against how Supabase Auth sets it
// during OAuth code exchange. The ISC requires only that readClientIdFromJwt() is removed.
```

**Caution:** The exact field name in `app_metadata` where Supabase Auth stores the OAuth client_id must be confirmed by checking Supabase Auth documentation or existing grants. The ISC requirement (ISC-9) is that `client_id` is extracted from the verified user object returned by `authClient.auth.getUser(rawToken)`, not from raw base64 decoding. [ASSUMED: exact field path in app_metadata]

### Pattern 3: Slug Tombstone Migration

**What:** Two tombstone tables + AFTER DELETE triggers on organizations and workspaces.
**Critical ordering:** tombstone tables must exist BEFORE slug columns are added — the DELETE trigger on slug columns references the tombstone table.

```sql
-- Source: ISC-20-26 (ISA.md)
CREATE TABLE IF NOT EXISTS public.org_slug_tombstone (
  slug VARCHAR(40) PRIMARY KEY,
  retired_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS public.workspace_slug_tombstone (
  org_id UUID NOT NULL REFERENCES public.organizations(id) ON DELETE CASCADE,
  slug VARCHAR(40) NOT NULL,
  retired_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (org_id, slug)
);

-- Trigger: when org is deleted, tombstone its slug
CREATE OR REPLACE FUNCTION tombstone_org_slug()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  IF OLD.slug IS NOT NULL THEN
    INSERT INTO org_slug_tombstone (slug) VALUES (OLD.slug)
    ON CONFLICT (slug) DO NOTHING;
  END IF;
  RETURN OLD;
END;
$$;

CREATE TRIGGER tr_tombstone_org_slug
AFTER DELETE ON organizations
FOR EACH ROW EXECUTE FUNCTION tombstone_org_slug();
```

### Pattern 4: Slug Schema Migration (depends on tombstone)

**What:** Add `slug` columns to organizations and workspaces. Backfill existing rows. Add combined length constraint.

```sql
-- Source: ISC-66-74, ISC-105-111 (ISA.md)
ALTER TABLE organizations
  ADD COLUMN IF NOT EXISTS slug VARCHAR(40)
  CHECK (slug ~ '^[a-z0-9]+$');

-- After backfill:
ALTER TABLE organizations ALTER COLUMN slug SET NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS organizations_slug_unique ON organizations(slug);

-- Reserved slugs enforced via function-level check (not DB constraint — easier to maintain)
-- Reserved: api, www, app, mcp, cdn, mail, smtp, admin, auth, status, blog

ALTER TABLE workspaces
  ADD COLUMN IF NOT EXISTS slug VARCHAR(40)
  CHECK (slug ~ '^[a-z0-9]+$');
-- After backfill:
ALTER TABLE workspaces ALTER COLUMN slug SET NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS workspaces_org_slug_unique ON workspaces(org_id, slug);

-- Combined length: org_slug + 1 separator + ws_slug <= 63
ALTER TABLE workspaces ADD CONSTRAINT workspaces_combined_subdomain_length
  CHECK (
    octet_length(
      (SELECT slug FROM organizations WHERE id = workspaces.org_id)
      || '-' || slug
    ) <= 63
  );
```

**Backfill logic (Claude's discretion):**
```sql
-- Backfill orgs: strip non-alphanumeric, lowercase, numeric suffix on collision
WITH base_slugs AS (
  SELECT id, lower(regexp_replace(name, '[^a-z0-9]', '', 'gi')) AS base_slug
  FROM organizations WHERE slug IS NULL
),
ranked AS (
  SELECT id, base_slug,
    ROW_NUMBER() OVER (PARTITION BY base_slug ORDER BY created_at) AS rn
  FROM base_slugs
)
UPDATE organizations o
SET slug = CASE WHEN r.rn = 1
  THEN LEFT(r.base_slug, 40)
  ELSE LEFT(r.base_slug, 37) || r.rn::text
END
FROM ranked r WHERE o.id = r.id;
```

### Pattern 5: New Cloudflare Worker (worker-routing)

**What:** New file `cloudflare/mcp-subdomain-worker/worker.ts` with wildcard `*.callvaultai.com/*` route.
**Key logic:** Extract org/workspace slug from hostname, validate format, inject headers, route to correct Edge Function.

```typescript
// Source: ISC-75-81 (ISA.md)
const SLUG_REGEX = /^[a-z0-9]+$/;
const SUPABASE_BASE = "https://vltmrnjsubfzrgrtdqey.supabase.co";

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url);
    const hostname = url.hostname; // e.g., "acmecorp.callvaultai.com"

    // Extract subdomain: first segment before first .
    const subdomain = hostname.split('.')[0]; // "acmecorp" or "acmecorp-sales"

    // Distinguish org-only vs org+workspace (hyphen separator; slugs can't contain hyphen)
    let orgSlug: string;
    let wsSlug: string | null = null;
    const hyphenIdx = subdomain.indexOf('-');
    if (hyphenIdx !== -1) {
      orgSlug = subdomain.slice(0, hyphenIdx);
      wsSlug = subdomain.slice(hyphenIdx + 1);
    } else {
      orgSlug = subdomain;
    }

    // Validate slug format
    if (!SLUG_REGEX.test(orgSlug) || (wsSlug && !SLUG_REGEX.test(wsSlug))) {
      return new Response(JSON.stringify({ error: 'not_found' }), { status: 404 });
    }

    // Route based on path
    const route = resolveRoute(url);
    if (!route) {
      return new Response(JSON.stringify({ error: 'not_found' }), { status: 404 });
    }

    // Build forwarded request with injected headers
    const headers = new Headers(request.headers);
    headers.set('x-callvault-org-slug', orgSlug);
    if (wsSlug) headers.set('x-callvault-workspace-slug', wsSlug);
    headers.set('x-callvault-host', hostname);
    headers.set('x-callvault-scope', wsSlug ? 'workspace' : 'org');
    headers.set('x-callvault-internal-secret', env.CALLVAULT_INTERNAL_SECRET);
    headers.set('host', new URL(SUPABASE_BASE).host);
    // ... (strip inbound x-callvault-* to prevent injection)

    return fetch(new Request(route.target, { method: request.method, headers, body: request.body, redirect: 'manual' }));
  }
};
```

### Pattern 6: auth.ts Slug Resolution (auth-slug-resolution)

**What:** auth.ts reads `x-callvault-org-slug` header injected by the Worker, resolves to org_id via DB query, then validates `token.org_id === resolved_org_id`.

```typescript
// Source: ISC-82-89 (ISA.md)
const orgSlugHeader = req.headers.get('x-callvault-org-slug');
const wsSlugHeader = req.headers.get('x-callvault-workspace-slug');

if (orgSlugHeader) {
  // Resolve slug → org_id using service role (bypasses RLS)
  const { data: orgRow, error: orgError } = await serviceRoleClient
    .from('organizations')
    .select('id')
    .eq('slug', orgSlugHeader)
    .maybeSingle();

  if (orgError || !orgRow) {
    return { ok: false, response: new Response(
      JSON.stringify({ error: 'org_not_found' }), { status: 404 }

  if (mcpToken.org_id !== orgRow.id) {
    return { ok: false, response: new Response(
      JSON.stringify({ error: 'token_org_mismatch' }), { status: 403 }
```

### Pattern 7: protocol.ts Subdomain Host Resolution (protocol-subdomain)

**What:** `resolveOriginHost()` currently only accepts `api.callvaultai.com` and `mcp.callvaultai.com`. Must be extended to accept ANY `*.callvaultai.com` host when it is subdomain-shaped.

```typescript
// Source: ISC-90-93 (ISA.md)
// Current code uses ALLOWED_HOSTS (Set of two strings). Must change to:
const SUBDOMAIN_PATTERN = /^[a-z0-9]+(-[a-z0-9]+)?\.callvaultai\.com$/;
const ALLOWED_STATIC_HOSTS = new Set(['api.callvaultai.com', 'mcp.callvaultai.com']);
const FALLBACK_HOST = 'api.callvaultai.com';

export function resolveOriginHost(req: Request): string {
  const headerValue = req.headers.get('x-callvault-host') ?? req.headers.get('x-forwarded-host');
  const fwd = headerValue?.split(',')[0]?.trim();
  if (!fwd) return FALLBACK_HOST;
  if (ALLOWED_STATIC_HOSTS.has(fwd)) return fwd;
  if (SUBDOMAIN_PATTERN.test(fwd)) return fwd; // subdomain URL
  return FALLBACK_HOST;
}
```

```sql
BEGIN
```

### Anti-Patterns to Avoid

- **Never extend `cloudflare/api-proxy/worker.ts` for subdomain routing.** The new Worker must be a separate file at `cloudflare/mcp-subdomain-worker/worker.ts`. The two Workers coexist via separate routes.
- **Never check `app_metadata.client_id` by decoding the JWT manually.** Always use `authClient.auth.getUser(rawToken)` and read from the returned user object.
- **Never write a slug column before tombstone tables exist.** The migration order is strictly: tombstone tables first, slug columns second.
- **Never provision wildcard DNS before all 7 Critical/High security gates are verified.** This is a hard gate.
- **Never use hyphen in slugs.** Slugs are `^[a-z0-9]+$`. The hyphen in the combined subdomain is the separator BETWEEN org and workspace slugs, not part of either slug.
- **Never trust inbound `x-callvault-*` headers from the client.** The new Worker must strip inbound `x-callvault-org-slug`, `x-callvault-workspace-slug`, and `x-callvault-internal-secret` before re-injecting authoritative values (ISC-5).

## Common Pitfalls

### Pitfall 1: Slug Column Added Without Tombstone Tables

**What goes wrong:** The DELETE trigger on `organizations` that tombstones slugs references `org_slug_tombstone`. If `org_slug_tombstone` doesn't exist when the trigger fires, the trigger fails, and the membership DELETE rolls back or errors.
**Why it happens:** Migrations are sometimes written in wrong order during fast iteration.
**How to avoid:** The slug-schema migration must start with `-- depends on: slug-tombstone migration` and the planner must set `depends_on: [sec-slug-tombstone]` in its frontmatter.
**Warning signs:** `ERROR: relation "org_slug_tombstone" does not exist` during migration push.

### Pitfall 2: Inbound x-callvault-* Header Injection

**What goes wrong:** An attacker sets `x-callvault-internal-secret: (correct value)` or `x-callvault-org-slug: (any slug)` on a direct request to the Supabase function URL, bypassing the Worker entirely.
**Why it happens:** The Worker strips CF-* headers but the current list (`STRIP_REQUEST_HEADERS` in api-proxy/worker.ts) does not include `x-callvault-*` headers.
**How to avoid:** The new Worker must strip inbound `x-callvault-org-slug`, `x-callvault-workspace-slug`, `x-callvault-internal-secret`, `x-callvault-scope` before re-injecting authoritative values. ISC-5 explicitly requires this.
**Warning signs:** ISC-6 fails — direct POST to Supabase function URL without the secret still proceeds.

### Pitfall 3: resolveOriginHost ALLOWED_HOSTS Set Blocks Subdomain URLs

**What goes wrong:** `mcp-server/protocol.ts` and `mcp-oauth-metadata/index.ts` both have `ALLOWED_HOSTS = new Set(['api.callvaultai.com', 'mcp.callvaultai.com'])`. A request from `acmecorp.callvaultai.com` will fall back to `api.callvaultai.com`, causing all self-referencing URLs in OAuth metadata and WWW-Authenticate headers to use the wrong host.
**Why it happens:** The ALLOWED_HOSTS pattern was correct for the two-hostname architecture; it needs extending for wildcard subdomains.
**How to avoid:** protocol-subdomain plan must update both `resolveOriginHost()` in `protocol.ts` AND the equivalent function in `mcp-oauth-metadata/index.ts`. They are currently duplicated (confirmed by reading both files).
**Warning signs:** OAuth metadata `authorization_endpoint` shows `api.callvaultai.com` instead of `acmecorp.callvaultai.com` when hitting the subdomain URL.

### Pitfall 4: Worker Route Conflict with api.callvaultai.com Custom Domain

**What goes wrong:** The new `*.callvaultai.com/*` wildcard route might intercept requests intended for `api.callvaultai.com` (the existing custom_domain route).
**Why it happens:** Cloudflare route matching order could be ambiguous.
**How to avoid:** According to Cloudflare's routing rules, custom domains (set via `custom_domain = true` in wrangler.toml) take priority over wildcard pattern routes. The existing `api.callvaultai.com` and `mcp.callvaultai.com` custom domains will continue to route to the api-proxy worker. The `*.callvaultai.com/mcp` pattern route will match only non-explicitly-routed subdomains. [ASSUMED: Cloudflare routing precedence — confirm by verifying wrangler deploy output or Cloudflare docs]
**Warning signs:** `api.callvaultai.com/mcp` starts 404-ing after the new Worker deploys.

### Pitfall 5: supabase db push Without --use-api Hangs

**What goes wrong:** Docker is not running on this machine. `supabase db push` without `--use-api` silently hangs waiting for Docker.
**Why it happens:** The Supabase CLI's default migration mode requires Docker for local bundling.
**How to avoid:** Always use `supabase db push --use-api` for migration tasks. Already documented in `supabase/CLAUDE.md`.
**Warning signs:** `supabase db push` command hangs with no output.

### Pitfall 6: McpSetupSnippets Needs org/workspace Slug Props

**What goes wrong:** The current `McpSetupSnippets` component takes only `workspaceId` (a UUID) and calls `getMcpUrl()` for the org URL. After this phase, it needs org and workspace slugs — not UUIDs — to build subdomain URLs.
**Why it happens:** The component predates the slug architecture.
**How to avoid:** The ui-url-builder plan must update the `McpSetupSnippets` props interface to accept `orgSlug` and optionally `wsSlug`, and update all call sites. The existing `workspaceId` prop may need to be kept for legacy URL display alongside the new subdomain URL.
**Warning signs:** `buildScopedMcpUrl` is added to the service but McpSetupSnippets still shows `mcp.callvaultai.com` for all URLs.

### Pitfall 7: selectOAuthGrant Silent Fallback for Multi-Org Users

**What goes wrong:** Current `grant-selection.ts` at line 49: `return grants[0]` — when no org grant is found and multiple workspace grants exist, it picks the first one. This could return a grant for the wrong org.
**Why it happens:** The original implementation predates multi-org use cases.
**How to avoid:** sec-multiorg-grant plan must change the final fallback in `selectOAuthGrant` to return 403 with disambiguation message when `grants.length > 1` and all grants span different orgs (no single org grant covers all).
**Warning signs:** A user with two orgs connecting via `mcp.callvaultai.com` gets data from the wrong org.

## Open Questions

1. **What field in `jwtUser.app_metadata` holds the OAuth `client_id`?**
   - What we know: Supabase Auth issues JWTs during the OAuth flow and populates `app_metadata`. The readClientIdFromJwt() function currently reads the `client_id` claim directly from the raw JWT payload (base64-decoded, without signature verification).
   - What's unclear: Whether Supabase sets `app_metadata.client_id` (same field name) or uses a different path like `app_metadata.provider_token_hash` or `app_metadata.oauth_client_id`.
   - Recommendation: The sec-jwt-fix implementer should check the Supabase Auth source or test with a real OAuth flow to confirm the field name before removing `readClientIdFromJwt()`. The existing `oauth-client-grants.integration.test.ts` may have relevant fixtures.

2. **Does the CHECK constraint referencing the parent org's slug cause a performance issue on workspace inserts?**
   - What we know: The combined length constraint needs to read `organizations.slug` during every workspace insert/update.
   - What's unclear: Whether Postgres allows this as a CHECK constraint (accessing another table) — PostgreSQL actually does NOT allow subqueries in CHECK constraints without a trigger.
   - Recommendation: Use a TRIGGER instead of a CHECK constraint for the combined length validation: `CREATE TRIGGER tr_check_combined_slug_length BEFORE INSERT OR UPDATE ON workspaces FOR EACH ROW EXECUTE FUNCTION check_combined_slug_length()`.

3. **Cloudflare rate limiting rule syntax for the new Worker**
   - What we know: ISC-17 requires max 10 registrations/IP/hr on `/mcp-register` path. ISC-46 requires max 20 req/min/IP for unauthenticated requests to `*.callvaultai.com`.
   - What's unclear: Whether these are configured via the Cloudflare dashboard (Rules > Rate Limiting) or via wrangler.toml / Cloudflare API. The existing api-proxy Worker has no rate limiting rules in its wrangler.toml.
   - Recommendation: Rate limit rules for mcp-oauth-register are configured via Cloudflare dashboard or API against the `mcp.callvaultai.com/mcp-register` path (for the existing DCR phishing gate), and separately against `*.callvaultai.com/mcp-register` (for the new Worker). Mark as Claude's Discretion per CONTEXT.md.
