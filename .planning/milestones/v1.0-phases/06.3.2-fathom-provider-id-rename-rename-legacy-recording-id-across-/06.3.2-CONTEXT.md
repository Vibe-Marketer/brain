# Phase 06.3.2: fathom_provider_id rename — Context

**Gathered:** 2026-06-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 06.3.2 renames `recordings.legacy_recording_id` (BIGINT) to `recordings.fathom_provider_id` everywhere it appears: one DB migration, regenerated Supabase TypeScript types, ~94 frontend files, ~48 Edge Function files, and documentation. No schema or data changes — column values and semantics are identical; only the name changes.

This phase does NOT rename `source_call_id` (TEXT), touch historical migration SQL, or change any other recording-ID-related columns or tables.

</domain>

<decisions>
## Implementation Decisions

### DB Migration Approach

- **D-01:** Single atomic migration using `ALTER TABLE recordings RENAME COLUMN legacy_recording_id TO fathom_provider_id`. No dual-column overlap, no add-backfill-drop multi-step. Atomic rename is cleaner and sufficient — no external API consumers pass the column name directly.
- **D-02:** The migration MUST also include `CREATE OR REPLACE` for every live view, RPC function, and stored procedure that references `legacy_recording_id` by name. Postgres does NOT automatically update view/function bodies on column rename. The planner must audit the following known references before writing the migration:
  - `fathom_calls` view (`20260309200001_fix_fathom_calls_view.sql`)
  - `global_search` RPC (`20260309200013_global_search_rpc.sql` — at least 8 references)
  - `hybrid_search` RPCs (`20260209081900_fix_hybrid_search_transcripts.sql`, `v2`, `v3`)
  - `delete_recording` RPC (`20260308100001_delete_recording_rpc.sql`)
  - Any other live function definitions that reference the column

### TypeScript Types: Regeneration

- **D-03:** After the migration runs, regenerate `src/types/supabase.ts` via `supabase gen types typescript --project-id <id>`. TypeScript errors from the regeneration become the exhaustive code-change checklist. Do NOT do manual find-and-replace as a substitute for regeneration.
- **D-04:** Manual type files (`src/types/workspace.ts`, `src/types/meetings.ts`, `src/types/contacts.ts`) have explicit `legacy_recording_id` properties. Update each to `fathom_provider_id` after regeneration resolves the generated types.

### TypeScript Helper Function Naming

- **D-05:** `isLegacyId()` in `src/lib/recording-ids.ts` stays as-is. It tests ID FORMAT (numeric vs UUID), not the column name. The semantic is "is this a numeric Fathom-format ID?" which remains correct regardless of the column rename.
- **D-06:** `legacyId` field on the `ResolvedRecording` interface in `src/lib/recording-ids.ts` is renamed to `fathomProviderId`. This property mirrors the DB column and should track it. All callers of `toRecordingUuidBatch()` that use `.legacyId` must be updated to `.fathomProviderId`.
- **D-07:** All TypeScript property accesses `recording.legacy_recording_id` in source files (hooks, services, components) rename to `recording.fathom_provider_id` — driven by TypeScript errors after regeneration.

### Historical Migration SQL

- **D-08:** Do NOT touch historical migration files. The 131 references to `legacy_recording_id` in already-executed `.sql` migration files are immutable history. Only the new rename migration and any live view/function recreations need to be written.

### Out of Scope

- **D-09:** `source_call_id` (TEXT column on `recordings`) stores the same Fathom numeric ID as a string. It is a different column with a different purpose. Not renamed in this phase.
- **D-10:** `isLegacyId()` function name and any format-detection logic are not renamed (per D-05).

### Execution Order (for planner)

The correct order to avoid a broken intermediate state:

1. Write + deploy the DB migration (RENAME COLUMN + recreate all affected views/functions in the same transaction)
2. Run `supabase gen types typescript` to regenerate `src/types/supabase.ts`
3. Fix TypeScript errors — they are the exhaustive list of required code changes
4. Update `ResolvedRecording.legacyId` → `fathomProviderId` and all callers
5. Update manual type files (workspace.ts, meetings.ts, contacts.ts)
6. Update documentation: `src/CLAUDE.md` (remove "Planned rename" note, update table), `recording-ids.ts` comments, `supabase/CLAUDE.md` if it exists
7. Run `npm run type-check` → zero errors required
8. Run `npm run build` → zero errors required
9. Run tests
