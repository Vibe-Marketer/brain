<user_constraints>
## User Constraints (from CONTEXT.md)

### Locked Decisions

- `api.callvaultai.com/v1/*` is the canonical machine API for CallVault integrations.
- Obsidian should use the canonical REST API rather than a separate `obsidian-sync` backend contract.
- The current unused Obsidian-specific implementation has no compatibility constraint and can be removed or replaced.
- REST is separate from MCP: JSON REST envelopes, not MCP tools or MCP markdown responses.
- Do not expose Supabase generated `/rest/v1` as the CallVault public API.
- REST auth uses CallVault personal API tokens with `token_source = 'api'`.
- Missing/unknown tokens return 401 JSON; wrong-source tokens return 403 JSON.
- MVP endpoints: `GET /v1/calls`, `/v1/contacts`, `/v1/workspaces`, `/v1/speakers`.
- Planning must evaluate whether Obsidian requires call detail/transcript routes in the first slice.

- Whether Obsidian formatting is a REST option or a client/export utility.

### Deferred Ideas (OUT OF SCOPE)

- Broad write/admin REST endpoints.
- Raw Supabase `/rest/v1` as product API.
- Permanent separate Obsidian backend API.
- SDKs, full OpenAPI publishing, and broad developer docs unless needed for verification.

<research_summary>
## Summary

Supabase provides an auto-generated PostgREST API at `/rest/v1`, but it reflects database schema and is intended either for direct Supabase client use or as a complement to an application-owned API. It is not the right public developer API for CallVault because CallVault needs product-shaped contracts, stable versioned routes, and CallVault-owned API tokens.

Supabase Edge Functions are the right runtime for this phase. Official Supabase routing guidance says Edge Functions support all standard HTTP methods and can implement complete REST APIs in a single function, reducing cold starts compared with many small functions. The existing CallVault Cloudflare worker already proxies API host routes to Supabase functions and is the correct place to add `/v1/*`.

The current Obsidian implementation is a useful prototype but not the target architecture. It already proves bearer lookup by `token_source`, workspace resolution, call listing, transcript retrieval, and markdown building. However, it creates separate `obsidian` tokens and a separate `/obsidian-sync` contract. Because it has not been used yet, Phase 06.2 should replace that path with API tokens and canonical REST routes.

**Primary recommendation:** Build one `callvault-api` Edge Function behind `api.callvaultai.com/v1/*`, backed by `token_source='api'` auth, and fold Obsidian into that API-token/REST model while preserving the existing client-side ZIP export utility if useful.
</research_summary>

<architecture_patterns>
## Architecture Patterns

### System Architecture Diagram

```text
Developer / Obsidian client
  -> HTTPS GET api.callvaultai.com/v1/{resource}
  -> Cloudflare Worker route resolver
  -> Supabase Edge Function: callvault-api
  -> API token auth helper
       -> mcp_tokens lookup by token
       -> enforce token_source = api
       -> enforce revoked_at is null
       -> derive user_id, org_id, workspace_id, scope
  -> Resource handler
       -> workspace/org scope resolver
       -> product-shaped Supabase service-role query
       -> envelope formatter
  -> JSON response: { data, pagination }
```

### Recommended Project Structure

```text
supabase/functions/callvault-api/
  index.ts                 # Deno.serve entry and route dispatch
  auth.ts                  # API-token auth only
  responses.ts             # { data, pagination } and { error } helpers
  routes/
    calls.ts
    contacts.ts
    workspaces.ts
    speakers.ts
  __tests__/
    auth.test.ts
    contract.test.ts

src/services/
  api-tokens.service.ts    # frontend service for token list/generate/revoke
src/hooks/
  useApiTokens.ts
src/components/settings/
  ApiTokensSection.tsx     # replaces Obsidian token section behavior
```

### Pattern 1: One REST Edge Function, Internal Router

**What:** Use one Edge Function for `/v1/*` and route by method/path internally.
**Why:** Supabase routing docs call out this pattern for complete REST APIs and reduced cold starts.
**Repo analogue:** `mcp-server` remains one Edge Function with internal modules; `obsidian-sync` already routes multiple paths internally.

### Pattern 2: Explicit Token Source Boundary

**What:** Authenticate bearer tokens by exact token row, then enforce `token_source`.
**Why:** API, MCP, and Obsidian tokens must not be interchangeable.
**Repo analogue:** `obsidian-sync` filters `token_source = 'obsidian'`; REST should use `token_source = 'api'` and add wrong-source 403 behavior.

### Pattern 3: Product JSON Envelope

**What:** Every list endpoint returns `{ data, pagination }`; errors return `{ error: { code, message } }`.
**Why:** Avoids leaking raw PostgREST shapes and separates REST from MCP markdown/JSON-RPC.

### Anti-Patterns to Avoid

- Exposing `https://vltmrnjsubfzrgrtdqey.supabase.co/rest/v1/...` as the developer API.
- Letting MCP tokens authenticate REST endpoints.
- Keeping `/obsidian-sync` as a second permanent integration API.
- Returning raw Supabase rows with unstable internal field names.
- Using service-role/secret keys as customer-facing API credentials.
</architecture_patterns>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Raw Supabase API Becomes Product Contract

**What goes wrong:** External users depend on table names, joins, and PostgREST query syntax.
**How to avoid:** Only document and route `api.callvaultai.com/v1/*`; keep Supabase URLs internal.

### Pitfall 2: Token Source Confusion

**What goes wrong:** A valid MCP token works on REST or a valid API token works on MCP.
**How to avoid:** Add explicit source tests for API token success, MCP token 403, Obsidian token 403, missing token 401, and unknown token 401.

### Pitfall 3: Obsidian Cleanup Leaves UI/Hook Stragglers

**What goes wrong:** Backend path changes but Settings still says "Generate Obsidian token" or calls `generate_obsidian_token`.
**How to avoid:** Plan frontend service/hook/component updates in the same phase and run `rg "obsidian-sync|generate_obsidian_token|token_source = 'obsidian'"`.

### Pitfall 4: Proxy Route Works Locally But Not on Vanity Host

**What goes wrong:** Supabase function behaves but `api.callvaultai.com/v1/*` still 404s.
**How to avoid:** Add Cloudflare worker route tests and live curl proof against `api.callvaultai.com`, not only raw Supabase functions.
</common_pitfalls>

<source_findings>
## Source Findings

- `cloudflare/api-proxy/worker.ts` currently returns 404 for unknown routes and has no `/v1/*` branch.
- `supabase/functions/obsidian-sync/index.ts` has useful code for token lookup, workspace resolution, calls listing, transcript route, export zip route, and Obsidian markdown formatting.
- `supabase/migrations/20260608120000_obsidian_sync_token_label.sql` already allows `token_source IN ('mcp', 'obsidian', 'api')`, but only creates an Obsidian lookup index and `generate_obsidian_token`.
- `src/services/obsidian-tokens.service.ts`, `src/hooks/useObsidianTokens.ts`, and `src/components/settings/ObsidianConnectorSection.tsx` are the current UI/service surface that should be replaced or reframed.
- `src/components/settings/IntegrationsTab.tsx` embeds `ObsidianConnectorSection` directly under integrations.
- `supabase/functions/mcp-server/tools/read/list_calls.ts`, `list_contacts.ts`, and `list_speakers.ts` provide read-scope logic to adapt but currently return MCP markdown.
</source_findings>

<validation_architecture>
## Validation Architecture

- Unit/source tests:
  - API token helper: 401 missing/unknown, 403 wrong source, success for `api`, revoked rejection.
  - Response helpers: success/error envelope shape and pagination object.
  - Cloudflare worker route: `/v1/calls` maps to `functions/v1/callvault-api/v1/calls`.
  - Settings services/hooks: use `token_source='api'` RPC/service and no Obsidian token query key.
- Integration/live tests:
  - Generate temporary production API token, call `https://api.callvaultai.com/v1/workspaces` and one scoped list endpoint.
  - Call missing auth and wrong-source token cases against production vanity route.
  - Revoke temporary token and confirm it no longer works.
- Build/deploy proof:
  - `npm run build`
  - `supabase functions deploy callvault-api --use-api`
  - `npx wrangler deploy`
</validation_architecture>
