The status_change audit trigger fires on the UPDATE — that is expected and additive.
- Both actions: INSERT admin_audit_log `{actor_user_id: verifiedUserId, action: 'ticket_' + action, target (ticket_id), metadata: {reason?}}` matching admin-manage-user's column usage. Never log secrets.
- Responses: `{success: true, action, ticket_id}`; structured error JSON on all failure paths.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Spoofing | approval event actor | mitigate | actor_id is ALWAYS the authenticateRequest-verified userId — never from the request body; dispatcher independently re-verifies admin role (13-RESEARCH) |
| T-14-02 | Elevation of Privilege | non-admin calling function | mitigate | has_role on service-role client with verified id; 403 probe in live verification |
| T-14-03 | Tampering | approving a ticket not awaiting approval | mitigate | 409 status guard before any write; dispatcher re-checks status at poll time (defense in depth) |
| T-14-04 | Repudiation | untracked admin actions | mitigate | admin_audit_log row per mutation + append-only ticket_events |
| T-14-05 | Injection | reason string into message body | mitigate | zod max-length; stored as plain text; rendered as React text nodes by 14-04 |
| T-14-SC | Tampering | package installs | accept | No new packages — esm.sh imports per repo function convention |
