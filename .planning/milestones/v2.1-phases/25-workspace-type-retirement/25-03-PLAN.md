Append a new mutation hook at the end of `src/hooks/useWorkspaceMutations.ts`. Follow the same `onMutate → snapshot → setQueryData → onError rollback → onSettled invalidate` pattern as `useUpdateWorkspace`.

```ts
// ─── Update Workspace Order ─────────────────────────────────────────────

export interface UpdateWorkspaceOrderInput {
  orgId: string
  pairs: Array<{ workspaceId: string; sortOrder: number }>
}

/**
 * useUpdateWorkspaceOrder — Persists per-user sidebar order to workspace_memberships.sort_order.
 *
 * Looks up the current user's membership row for each workspaceId in `pairs`, then
 * updates `sort_order` on each. Optimistically reorders the cached `workspaces` list
 * (instant UI), rolls back on error, and invalidates on settle.
 *
 * Atomicity caveat: client-side parallel updates (Promise.all) — for typical N <= 10
 * workspaces this is fine. If concurrent reorders from two devices race, last-write-wins
 * (per CONTEXT.md <deferred>).
 */
export function useUpdateWorkspaceOrder() {
  const { user } = useAuth()
  const queryClient = useQueryClient()

  return useMutation({
    mutationFn: async (input: UpdateWorkspaceOrderInput) => {
      if (!user) throw new Error('Not authenticated')

      // Resolve workspace_id -> the current user's membership.id
      const { data: memberships, error: selErr } = await supabase
        .from('workspace_memberships')
        .select('id, workspace_id')
        .eq('user_id', user.id)
        .in('workspace_id', input.pairs.map(p => p.workspaceId))

      if (selErr) throw selErr

      const membershipByWs = new Map(
        (memberships ?? []).map((m) => [m.workspace_id, m.id])
      )

      // Issue parallel UPDATEs — one per pair. Throws on any failure.
      await Promise.all(input.pairs.map(async (p) => {
        const mid = membershipByWs.get(p.workspaceId)
        if (!mid) return  // workspace not in user's memberships — silently skip
        const { error } = await supabase
          .from('workspace_memberships')
          .update({ sort_order: p.sortOrder })
          .eq('id', mid)
        if (error) throw error
      }))
    },
    onMutate: async (input) => {
      const listKey = queryKeys.workspaces.list(input.orgId)
      await queryClient.cancelQueries({ queryKey: listKey })
      const previousList = queryClient.getQueryData<WorkspaceWithMeta[]>(listKey)

      // Reorder cached list using input.pairs as the ordering source of truth.
      const orderMap = new Map(input.pairs.map(p => [p.workspaceId, p.sortOrder]))
      queryClient.setQueryData<WorkspaceWithMeta[]>(listKey, (old = []) =>
        [...old].sort((a, b) => (orderMap.get(a.id) ?? 999) - (orderMap.get(b.id) ?? 999))
      )

      return { previousList, listKey }
    },
    onError: (err: Error, _input, ctx) => {
      if (ctx?.previousList && ctx.listKey) {
        queryClient.setQueryData(ctx.listKey, ctx.previousList)
      }
      toast.error(`Failed to reorder workspaces: ${err.message}`)
    },
    onSettled: (_d, _e, input) => {
      queryClient.invalidateQueries({ queryKey: queryKeys.workspaces.list(input.orgId) })
    },
  })
}
```

Notes:
- The mutation does NOT touch `workspaces` rows directly — only `workspace_memberships`, scoped to `user_id`.
- `throwOnError()` is NOT used here because Supabase v2 prefers explicit `if (error) throw error` — match the existing file's pattern. If the file uses `.throwOnError()` elsewhere, switch to that for consistency.
- `useAuth`, `useQueryClient`, `supabase`, `queryKeys`, `WorkspaceWithMeta`, `toast` are all already imported at the top of `useWorkspaceMutations.ts`. Do NOT add duplicate imports.

function handleWorkspaceDragEnd(event: DragEndEvent) {
  const { active, over } = event

    orgId: activeOrgId,

}

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → useUpdateWorkspaceOrder mutationFn | Authenticated user updates `sort_order` on their own membership rows; user_id scoping enforced in query |
| Client UI → workspace_memberships.sort_order | Updates are bounded to the current user's rows; no cross-user write possible |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-10 | Tampering | useUpdateWorkspaceOrder mutationFn | mitigate | The SELECT for memberships is `eq('user_id', user.id)`; only memberships owned by the caller are returned and updated. UPDATE is by `id` (a UUID returned from the user-scoped SELECT), so a malicious client cannot inject another user's membership ID. |
| T-25-11 | Repudiation | Reorder mutation | accept | sort_order changes are not audit-logged; impact is UI-only (sidebar order). Acceptable per CONTEXT.md "last-write-wins is fine for now". |
| T-25-12 | Denial of Service | Promise.all UPDATEs | accept | N typically <= 10. For N > 50, defer to a server-side `reorder_workspace_memberships(jsonb)` RPC (RESEARCH.md Open Question 4). |
| T-25-13 | Information Disclosure | Drag handle visibility | accept | Handle is purely cosmetic; no data exposure. |
</threat_model>
