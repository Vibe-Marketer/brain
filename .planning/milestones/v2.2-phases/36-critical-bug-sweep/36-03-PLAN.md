# Plan 36-03: BUG-04 — Date Sort Chronological

## Goal

Date sort on every table is strictly chronological — both ascending and descending. No more Apr → Nov → Mar jumps in the same column direction.

## Root Cause (from code inspection)

`src/hooks/useTableSort.ts` (lines 35-37) already casts via `new Date(...).getTime()`, which is correct. However:

1. The hook only sorts **the current visible page**, not the full dataset (comment line 6: "Primary sort order comes from the server query (by date desc)").
2. When the server query returns `recording_start_time` as `null` for some rows (Zoom/manual/upload calls), the fallback `|| a.created_at || a.date || 0` produces inconsistent types — a string date vs `0` epoch.
3. If the underlying data passes `created_at` as an ISO string but the row's display column shows `recording_start_time`, sort and display disagree.

The fix is twofold: (a) ensure the sort function ALWAYS produces a comparable number even for null fields by treating null/missing as Number.NEGATIVE_INFINITY (so they always sort to the end), and (b) widen the test coverage to include the actual production data patterns (mixed null `recording_start_time` + populated `created_at`).

Modify `src/hooks/useTableSort.ts` lines 35-37. Replace the existing date branch with:

```typescript
} else if (sortField === "date" || sortField === "created_at" || sortField === "recording_start_time") {
  const toEpoch = (item: any): number => {
    const raw = item.recording_start_time ?? item.created_at ?? item.date;
    if (!raw) return Number.NEGATIVE_INFINITY;
    const t = new Date(raw).getTime();
    return Number.isFinite(t) ? t : Number.NEGATIVE_INFINITY;
  };
  aVal = toEpoch(a);
  bVal = toEpoch(b);
}
```

Reasoning: this guarantees `aVal` and `bVal` are always numbers (never `0` from `new Date(0)`, never NaN). Rows with null timestamps sort to the bottom in descending order (the "no date known" rows) instead of being interleaved as 1970-01-01 epoch values.
</action>
