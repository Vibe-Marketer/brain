# Phase 32 — UI Design Contract

> Visual and interaction contract for the Shared-Call Public Landing Page phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker. All design tokens, copy, and component patterns below are **prescriptive** — executor implements exactly as specified.

This phase reuses everything Phase 31 locked (auth-card chrome, Sonner toasts, ForgotPassword confirmation-screen pattern, error-mapping table). Where this contract restates a Phase 31 decision, it is a **deliberate carry-forward** — do not deviate.

---

## Scope of This Contract

Five surfaces, three of which are NEW component files, two of which are modifications.

| Surface | File | Change Type |
|---------|------|-------------|
| `/s/:token` public landing card | `src/components/share/PublicShareLanding.tsx` | NEW — Loom-style card shown to unauthenticated visitors and as the "wrong account → after sign-out" fallback |
| `/s/:token` wrong-account state | `src/components/share/WrongAccountState.tsx` | NEW — masked-email + sign-out card shown when authenticated user's email ≠ recipient |
| `/s/:token` orchestrator | `src/pages/SharedCallView.tsx` | MODIFY — replace the unconditional `navigate('/login')` redirect with a three-state state machine: public-landing / wrong-account / call-view. Existing "call-view" rendering stays (banner, header, transcript) — only the entry-gating logic changes. |
| Share-link signup path | `src/pages/Login.tsx` | MODIFY — extend the signup-completion mode (Phase 31) to accept `?share=:token` and pre-fill the recipient email locked from the token. Free tier auto-assigned, no plan picker. |
| Share Call modal visual cleanup | `src/components/sharing/ShareCallDialog.tsx` | MODIFY — fix the three Phase 29 sweep findings (border/icon/overflow). |

Out of scope (per CONTEXT.md `## Deferred Ideas`): "Request access" button, multi-recipient share links, share-link expiration UI, open-graph unfurls, share-link viewership analytics surfacing.

Backend coordination (referenced but NOT a UI surface): `supabase/functions/share-call/index.ts` returns `200 / public-safe-payload` for unauthenticated requests, `403 / WRONG_RECIPIENT` with `recipient_masked` for wrong-account, `404 / CALL_NOT_FOUND` for invalid/revoked tokens. The UI contract assumes this response shape. If backend lands a different shape, the wrong-account state copy degrades to the generic "Call Not Found" path until the backend signal exists.

**Form input height inside ShareCallDialog:** `h-10` (40px) — matches Phase 31 / existing shadcn input. Do NOT change.

Exceptions: **none**. All values are multiples of 4.

## Copywriting Contract

Every string below is **prescriptive**. Executor copies these exactly.

### Public Landing Card (`/s/:token` — unauthenticated, 200 response)

**Visual sequence top-to-bottom inside the card:**

1. Centered logo (`h-12 w-auto`, `mb-4`) — same logo asset Phase 31 uses on the auth card.
2. `RiLinksLine` icon (32px, `text-muted-foreground`, centered, `mb-3`) — the "this is a share link" visual cue.
3. Heading (`text-xl font-semibold text-foreground`, centered, `mb-2`):
   - Copy: `{Inviter First Name} {Inviter Last Initial}. shared a call with you`
   - Example: `Andrew N. shared a call with you`
   - Truncation: inviter name truncates with ellipsis if it would push the heading past two lines; the call title gets the ellipsis preference (the inviter is the trust signal, the title is the topic).
4. Call-title sub-line (`text-sm text-muted-foreground`, centered, `mb-6`):
   - Copy: `{Call Title}`
   - If title missing (rare — fall back to backend default): `An untitled call`
   - Line-clamp to 2 lines with ellipsis.
5. Primary CTA — full-width button (`bg-foreground text-background`, `h-10`):
   - Idle: `Sign up to view` (label) + `RiArrowRightLine` (icon, `text-vibe-orange`, `ml-2`)
   - Loading (during the redirect-to-`/login?signup=true&share={token}` navigation, which is instant — so loading state is theoretically never visible, but for safety): `Signing up...`
6. Secondary CTA — full-width button, `variant="hollow"`, `h-10`, `mt-2`:
   - Idle: `Open in existing account`
   - No icon.
7. Helper text under the CTA stack (`text-xs text-muted-foreground`, centered, `mt-4`):
   - Copy: `Free tier — no credit card needed`
   - This is the trust signal that distinguishes the share-recipient signup path from the Phase 31 external-pricing redirect.

### Wrong-Account Card (`/s/:token` — authenticated, `403 WRONG_RECIPIENT`)

**Visual sequence top-to-bottom inside the card:**

1. `RiUserLine` icon (32px, `text-muted-foreground`, centered, `mb-3`) — the "wrong identity" visual cue. Do NOT use `RiErrorWarningLine` — this is not an error from the user's perspective, it's a redirect prompt.
2. Heading (`text-xl font-semibold text-foreground`, centered, `mb-2`):
   - Copy: `This share is for a different account`
   - **Locked in Phase 31 UI-SPEC `### OAuth wrong-recipient` row** — do not re-word.
3. Body paragraph (`text-sm text-muted-foreground`, centered, `mb-6`):
   - Copy: `This call was shared with {recipient_masked}. Sign out and sign back in with that account.`
   - `{recipient_masked}` is the value from the backend response (server-side masked — never re-mask client-side). Example value as rendered: `na***@gmail.com`.
   - If `recipient_masked` is missing from the response (backend bug — defensive copy): `This call was shared with a different email. Sign out and sign back in with that account.` (drops the masked email entirely rather than rendering "undefined" or empty parentheses).
4. Primary button — full-width, `bg-foreground text-background`, `h-10`:
   - Idle: `Sign out`
   - Loading (during the `supabase.auth.signOut()` call): `Signing out...`
   - Behavior: signs out via `supabase.auth.signOut()`, then `navigate('/s/{token}')` to land on the unauthenticated public landing.
5. Secondary button — full-width, `variant="ghost"`, `h-10`, `mt-2`:
   - Idle: `Cancel`
   - Behavior: `navigate('/')` — back to the user's main app.

**No "Request access" button.** Deferred to v2.3 per CONTEXT.md. If the planner adds one, scope creep — skip.

This extends Phase 31's signup-completion mode (`?signup=true`). When the URL contains `?share={token}`, the form pre-fills the email **read-only from the token** and skips the plan-picker / pricing redirect.

| Sub-heading | `You're on the Free plan. Set a password to view the call.` — note "Free plan" is hardcoded (not parameterized like Phase 31's `{Plan Name}` because the share-link path is Free-only). |

| Submit button | `Create account` (idle) → `Creating account...` (loading) — Phase 31 copy carry-forward. |

## Interaction Patterns

### Public landing flow

| Trigger | Behavior |
|---------|----------|
| Visit `/s/:token` unauthenticated | Fetch from `share-call` Edge Function with no auth header → backend returns `{ status: 'public', inviter_name, call_title }` → render PublicShareLanding card with ≤200ms opacity fade-in via `motion.div`. |
| Click "Sign up to view" | `sessionStorage.setItem('pendingShareToken', token)` (defensive — Phase 31 also handles this, but redundant write is safe), then `navigate('/login?signup=true&share={token}')`. The Login page reads `share` and triggers the locked-email signup form. NO intermediate loading screen — instant client-side navigation. |
| Click "Open in existing account" | `sessionStorage.setItem('pendingShareToken', token)`, then `navigate('/login?share={token}')`. Login page in sign-in mode — user authenticates, post-login redirect lands on `/s/{token}` (which then re-fetches with auth and resolves to call-view, wrong-account, or not-found). |
| Backend returns 404 | Render the locked "Call not found" inline card. Do NOT render the public landing card. |
| Backend returns 5xx | Render the locked "Couldn't load the call" inline card. |
| Backend latency > 600ms | Render `<Spinner size="lg">` centered inside the page wrapper (no card chrome — the spinner is the entire viewport content while the call data is unknown). Once response lands, transition to the appropriate card (no flash — React Query's deduplication handles the swap). |

### Wrong-account flow

| Trigger | Behavior |
|---------|----------|
| Visit `/s/:token` authenticated, backend returns `403 WRONG_RECIPIENT` with `recipient_masked` | Render WrongAccountState card with ≤200ms opacity fade-in. |
| Click "Sign out" | Disable both buttons (set `isSigningOut: true`). Call `supabase.auth.signOut()`. On success, `navigate('/s/{token}')` (lands on the public landing because user is now unauthenticated). On failure, re-enable buttons + `toast.error('Couldn't sign out. Refresh and try again.')`. |
| Click "Cancel" | `navigate('/')` — no confirmation. |

### Share-link signup flow (Login.tsx extension)

| Trigger | Behavior |
|---------|----------|
| Visit `/login?signup=true&share={token}` | Read the token's recipient email server-side (via a lightweight `share-call` lookup that returns ONLY the recipient email for this purpose — or extract from the token if the token format embeds it; planner decides). Pre-fill the email input, disable it, render the `RiLockLine` icon inside the input. |
| Submit the form with valid password | POST to Supabase auth with the locked email + entered password. Set `signup_source: 'share-link'` in user_metadata (per CONTEXT.md `Implementation rules` bullet 4). Auto-assign Free tier — call `polar-create-customer` to provision the customer record but skip the Polar checkout redirect. On success (immediate session): `toast.success('Account created — welcome to CallVault!')` + `navigate('/s/{token}')`. On success (email-confirm pending): full-screen swap to the `Check your email` confirmation screen (ForgotPassword pattern), with the confirmation-link target ultimately landing the user on `/s/{token}` after they click the email link. |
| Submit fails | Phase 31 `getErrorToastMessage()` mapping table — toast.error with mapped copy. |
| Click "Sign in instead" mode-switcher | `navigate('/login?share={token}')` — sign-in mode, share token preserved. |

### ShareCallDialog cleanup specifics (SHARE-03)

Three concrete fixes — each fix is a small, targeted change. The planner must NOT refactor the structure; this is cleanup.

**Fix 1: Spurious orange/red field-borders on the recipient email input.**

Root cause hypothesis (verify in plan-phase via dev-browser screenshot): the `border-green-500/50 bg-green-500/5` classes applied to the "newly-created link" row (line 208) bleed visually via the `shadow` Tailwind utility cascading into adjacent elements, OR the global focus ring on `<Input>` is rendering with a non-semantic color due to a Tailwind config override.

**Locked fix:** Remove `border-green-500/50` and `bg-green-500/5` entirely. Replace with `border-border` and `bg-muted/50` (the highlight effect is preserved via a brief `motion.div` `animate={{ scale: [1, 1.02, 1] }} transition={{ duration: 0.3 }}` pulse on the just-created row, OR a `ring-2 ring-foreground/10` subtle ring that fades after 3 seconds — planner picks one, both meet the contract). The "Copied to clipboard" inline indicator changes from `text-green-600` to `text-foreground` with a `RiCheckLine` icon inheriting the same `text-foreground` (the icon is the affirmation; the color doesn't need to be green).

**Fix 2: Broken-looking "red-dots" icon next to the email field.**

Root cause hypothesis: `RiLinkM` is the source — it's an older Remix Icon variant ("M" suffix likely means "monochrome" or a specific weight) and renders inconsistently at `h-4 w-4`. The icon appears next to the email field via the `<RiLinkM className="h-4 w-4 mr-2" />` inside the CREATE button.

**Locked fix:** Replace ALL `RiLinkM` imports inside ShareCallDialog.tsx with `RiLinksLine` (the same icon family used on the public landing card — visual consistency across the share surfaces). Three occurrences to change: the CREATE button icon (line ~180), the share-link-row icon (line ~213), the empty-state icon (line ~268).

**Fix 3: Modal content overflows the parent dialog.**

Root cause hypothesis: the active-links list uses `max-h-48 overflow-y-auto` (line 201) which clamps the inner list height, BUT the Dialog itself doesn't constrain its content height — so when the user has 5+ active links, the inner list scrolls correctly but the dialog body's other elements (header, create-form, footer) plus the 192px-tall scrollable list together exceed the viewport on shorter screens, causing the entire dialog to scroll AND the inner list to scroll (double-scroll).

**Locked fix:** Add `max-h-[calc(100vh-8rem)]` and `overflow-hidden` to `<DialogContent>` (or use `flex flex-col` and a `min-h-0` middle section). The scrollable area should be the active-links list only — header and footer stay fixed. Specifically: wrap the `<div className="space-y-4">` body in a `flex flex-col min-h-0 overflow-hidden`, then the active-links inner container becomes `flex-1 min-h-0 overflow-y-auto` (removing the `max-h-48` constraint — let flex sizing do the work). Planner verifies via dev-browser at 768px height.

## Accessibility Contract

| Item | Requirement |
|------|-------------|

| Focus order — wrong-account | "Sign out" button → "Cancel" button. Default DOM order. On mount, auto-focus the "Sign out" button (`useEffect` with `ref.current?.focus()`) — the primary action is sign-out; this saves a tab keystroke. |

## What Plan-Phase Must Verify (carry-over from UI contract)

The UI contract has assumptions that plan-phase research must confirm. Listed here so they don't fall through:

1. **Backend response shape lands first.** The `share-call` Edge Function must return the three-state discriminated response (`200 public`, `200 authenticated-ok`, `403 wrong-recipient`, `404 not-found`, `5xx errors`) before the frontend state machine has anything to switch on. If backend isn't ready, frontend rendering degrades to today's "Call Not Found" for everything except the happy path — verify ordering.
2. **`recipient_masked` is server-side.** Per CONTEXT.md and `supabase/CLAUDE.md`, masking happens in the Edge Function, never client-side. UI contract assumes the backend returns the masked string verbatim.
3. **Token email lookup for signup pre-fill.** The signup form needs the recipient email to pre-fill (and lock) the input. Two options: (a) call `share-call` with no auth header — backend returns email along with inviter/title for public view; (b) embed the email in the token itself. CONTEXT.md says option (a) is fine because the share token is the credential. Plan-phase confirms which surface returns the email and adjusts the public-landing fetch contract accordingly. **NOTE:** if option (a), the public-landing response shape becomes `{ status: 'public', inviter_name, call_title, recipient_email }` — and the recipient email IS visible to anyone with the token, which is fine because the token is single-use credential anyway.
4. **Free tier auto-assignment.** The `polar-create-customer` flow must support a "Free tier without checkout" path. Per CONTEXT.md, the Polar customer record is created so the account is ready for later upgrade, but no checkout fires for Free. Verify the existing Polar integration supports this — if not, plan-phase scopes the Polar-side change.
5. **`pendingShareToken` sessionStorage usage.** Existing `SharedCallView.tsx:54` writes `pendingShareToken` before redirecting to `/login`. The new flow uses URL query params instead (`?share={token}` on `/login`). Decide: keep sessionStorage as a defensive fallback, or drop it. UI contract recommends URL-first with sessionStorage as defensive fallback (handles edge cases like external auth providers that strip query params on callback).
6. **Authenticated call-view stays structurally unchanged.** This phase only sanitizes tokens inside the existing call-view (replace `text-red-500`, `text-amber-500`, `bg-info-bg`, `border-info-border`, `text-info-text`). The layout, transcript rendering, banner placement, footer copy — all stay. If plan-phase wants to restructure the call-view, scope creep — skip.
7. **ShareCallDialog double-scroll fix.** Verify via dev-browser at 768px tall viewport with 6+ active share links that ONLY the inner list scrolls, not the entire dialog. Visual verification, not unit test.
8. **Phase 31 dependencies shipped.** This UI-SPEC assumes Phase 31's Toaster mount, ForgotPassword confirmation-screen pattern, error-mapping table, and signup-completion mode are landed. If Phase 31 is in-flight, document the dependency explicitly in the plan and gate Phase 32 execution on Phase 31 verification.
