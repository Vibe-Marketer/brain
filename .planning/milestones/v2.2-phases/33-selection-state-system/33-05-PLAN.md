# 33-05: Settings Tabs Canonical Pattern + Deep-Link Redirect (VIS-03 + QA-04)

## Objective

Two parts:

1. **VIS-03**: Apply the canonical `<SelectionButton>` to the Settings 2nd-pane category list (already mostly canonical — refactor to use the primitive). Also apply to sibling category panes (OrganizationCategoryPane, PeopleCategoryPane, AnalyticsCategoryPane, SortingCategoryPane) so they're all consistent — these all use the same hand-rolled selection JSX today.

2. **QA-04**: Redirect deep-link URLs `/settings/ai-integrations` and `/settings/admin` to `/settings/account` when the user lacks access (current behavior redirects invalid IDs to `/settings`, which auto-selects account — but the *valid* IDs are `mcp` and `admin`, and `ai-integrations` is an INVALID alias). The QA-04 spec wants `/settings/ai-integrations` (a friendly alias) to redirect to `/settings/account`. Add alias handling.

Re-read: QA-04 says BOTH URLs redirect to `/settings/account`. That's a generic redirect for these specific aliases — likely because these screens are not yet built / not yet permission-gated correctly. Implement as an explicit alias map at the URL parser.

In `src/pages/Settings.tsx`, in the existing `useEffect` that parses `urlCategory` (around line 29):

Add an explicit alias-redirect map BEFORE the validity check:

```tsx
// QA-04: alias redirects — old/friendly URLs that should land on /settings/account
const SETTINGS_URL_ALIASES: Record<string, string> = {
  'ai-integrations': 'account',
  'admin': 'account',
};

// ... inside the useEffect:
if (urlCategory) {
  // Apply alias redirect
  if (urlCategory in SETTINGS_URL_ALIASES) {
    navigate(`/settings/${SETTINGS_URL_ALIASES[urlCategory]}`, { replace: true });
    return;
  }
  // ... existing validation logic continues
}
```

Wait — the spec says `/settings/admin` should redirect to `/settings/account`. But `admin` is a valid category for ADMIN users. So the redirect should only fire when the user lacks ADMIN access. Re-read QA-04: "Settings deep-link URLs `/settings/ai-integrations` and `/settings/admin` redirect to `/settings/account`."

This is ambiguous — could mean "always redirect both" or "redirect when user lacks access". Looking at REQUIREMENTS.md again: the requirement is exact text only. Given that `admin` is a real category that some users CAN access, the safer behavior is: redirect ONLY when the user lacks access. The existing code at line 44-46 already does this for `admin` (when no ADMIN role) — it redirects to `/settings`. We need to change THAT to redirect to `/settings/account` instead.

For `ai-integrations` (not a valid category — the real one is `mcp`), it falls through to the invalid-category branch at line 49 which also redirects to `/settings`. Change THAT to `/settings/account` too.

Cleanest implementation:
```tsx
// In the useEffect, replace both navigate('/settings', { replace: true }) calls 
// at lines 46 and 49 with navigate('/settings/account', { replace: true })
// AND add ai-integrations as an explicit invalid-but-known alias that always redirects to account.
```

Simpler approach: change BOTH `navigate('/settings', { replace: true })` calls inside the useEffect to `navigate('/settings/account', { replace: true })`. This:
- Makes `/settings/ai-integrations` (invalid category) → `/settings/account` (via the invalid-id branch).
- Makes `/settings/admin` for non-admin users → `/settings/account` (via the no-access branch).
- Admins still get `/settings/admin` since `hasAccess` is true.

That satisfies QA-04 precisely.
