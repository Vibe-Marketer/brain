**Step 3b — Apply the dual-key fallback at the lookup site.**

`src/components/transcript-library/TranscriptTable.tsx:341-343`:
```ts
// Current:
tagAssignments={tagAssignments[call.canonical_uuid] || tagAssignments[call.recording_id] || []}
folderAssignments={folderAssignments[call.recording_id] || []}

// Fix:
tagAssignments={
  (call.canonical_uuid && tagAssignments[call.canonical_uuid]) ||
  tagAssignments[String(call.recording_id)] ||
  []
}
folderAssignments={
  folderAssignments[String(call.recording_id)] ||
  (call.legacy_recording_id ? folderAssignments[String(call.legacy_recording_id)] : undefined) ||
  []
}
```

**Why:** `folderAssignments` is keyed by `String(call_recording_id)` (legacy BIGINT, per `folders.service.ts:149`). When the row originated from the canonical `recordings` table, `call.recording_id` is the UUID — the lookup misses. The fallback to `legacy_recording_id` recovers the correct map key.

**Verify:**

**Acceptance criteria:**

- Both `tagAssignments` and `folderAssignments` use the dual-key fallback.
- Upstream mappers populate `legacy_recording_id` from `recordings.legacy_recording_id`.
